# 3D Music Dancer — Phase 1-10 + смена персонажа (белка, Mixamo)

## 📋 ПРОЦЕСС: правка персонажа в Blender → вшивание в проект (читать в первую очередь)

Единый проверенный процесс для любого персонажа, который правится в
Blender (вес хвоста, коленей, что угодно ещё) и переносится обратно в
рабочий FBX-файл проекта. Написано по итогам долгой отладки белки —
следуй этому чек-листу для следующего персонажа/следующей правки, чтобы
не проходить тот же путь заново.

### Правило №1 — Blender-файл после экспорта берём ЦЕЛИКОМ, не трогаем точечно

Раньше пытались "умно" исправлять только подозрительные вершины поверх
Blender-экспорта (сравнение файлов, эвристики по весам) — это **не
работает**, каждая итерация вносила новые ошибки поверх старых. Проверено
диагностическим тестом: сырой, совсем не тронутый Blender-экспорт
(геометрия + веса + материал + текстура как есть) визуально ПРАВИЛЬНЫЙ по
хвосту/коленям. Значит Blender не виноват — виноват был любой ручной
пересчёт весов поверх его результата.

**Вывод: если Blender прислал верный результат по геометрии/весам — не
трогать эту часть вообще, ни на бит.**

### Правило №2 — из чистого/оригинального файла переносим ТОЛЬКО то, чего не хватает в Blender-экспорте

Blender-экспорт как есть НЕ готов к прямому использованию — в нём
отсутствуют или отличаются несколько технических полей, не связанных с
геометрией/весами:

| Что перенести из чистого файла | Зачем | Как выглядит проблема без переноса |
|---|---|---|
| `AnimationStack`/`AnimationCurve` (сама анимация) | Blender-экспорт может не содержать нужных клипов вообще | анимация не играет |
| `PreRotation` по каждой кости | Blender не всегда пишет это поле | лёгкое неправильное покачивание в Idle |
| `RotationActive` флаг | должен быть включён вместе с PreRotation | PreRotation тихо игнорируется |
| `UnitScaleFactor` | Blender часто пишет `1.0` вместо `100.0` | масштаб/скорость анимации может плыть |
| 6 legacy-свойств материала: `Ambient`, `Diffuse`, `Emissive`, `Opacity`, `Reflectivity`, `Specular` | Blender не экспортирует эти старые Phong-поля, только их `...Color`-аналоги | персонаж выглядит светлее/более плоским, тени теряют глубину (без `Opacity` рендерер может трактовать материал как слегка прозрачный) |

**НЕ переносить** (ловушка, в которую уже попадали): не путать
`Lcl Rotation` со значениями скелета — Blender **сам решает**, что писать
как базовую (default) позу конкретной кости, и это НЕ баг, если у кости
одновременно стоят `PreRotation` и ненулевая `Lcl Rotation` — так работает
FBX по спецификации, они не дублируют друг друга. Ошибка была бы —
скопировать `PreRotation` из чистого файла поверх кости, у которой
Blender уже закодировал ту же самую ориентацию через `Lcl Rotation`
по-своему: тогда получится реальный двойной поворот. Если Blender-файл
целиком не тронут (правило №1), этой ловушки не будет вообще — она
возникает только если начать вручную домешивать поля из разных файлов
на одну и ту же кость.

### Чек-лист проверки после переноса (все пункты должны быть 0 расхождений)

```
Вершин без веса: 0
Сломанных по сумме весов (>1.05): 0
Веса вершин — побайтово идентичны Blender-файлу: 0 расхождений
PreRotation: N/N костей перенесено (N = общее число костей скелета)
Кривых вращения: столько-то, расхождений с чистым источником: 0
UnitScaleFactor: 100.0
Материал: все 6+ legacy-свойств перенесены, 0 расхождений
Текстура: валидна (сверить размер в байтах/формат)
```

### Отдельная ловушка: "персонаж стал крупнее/мельче после правки в Blender"

Даже если чек-лист выше весь на 0 — персонаж всё равно может визуально
изменить размер. Причина НЕ в весах/геометрии, а в **коде сцены**:
`scene.js` считает автомасштаб (`targetHeight / rawHeight`) один раз при
загрузке FBX — и раньше делал это **сразу**, по статичной default-позе,
записанной в самом файле. А эта default-поза зависит от экспортёра:
родной/чистый экспорт хранит T-позу (Lcl Rotation = 0 у всех костей,
только PreRotation), Blender вместо T-позы впекает уже позу Idle (руки
вдоль тела) прямо в статику костей. У T-позы и Idle-позы РАЗНЫЙ силуэт —
значит и разный посчитанный bounding box, хотя реальный рост тела
не менялся.

**Уже исправлено в коде (не нужно чинить заново для новых персонажей):**
`loadCharacterFBX()` в `scene.js` больше не считает scale сразу при
загрузке. Вместо этого — новая функция `measureAndApplyAutoScale(model,
targetHeight)`, которую `main.js` вызывает **после** первого тика mixer
с уже играющей анимацией Idle (`slot.mixer.update(0)` после
`animController.play("idle")`), **до** `groundAndCenterModel()`. Это та
же самая поза, что уже использует `groundAndCenterModel` — единый
источник истины "что считается настоящим ростом персонажа", не зависящий
от того, как конкретный экспортёр записал default-позу.

**Проверка на новом персонаже:** открой консоль (F12), найди строку
```
[scene] Масштаб по позе Idle (не default-позе экспортёра): рост X.XXX ед. → scale=X.XXXXX
```
Итоговый `scale` должен быть близко к `targetHeight / 1.0` (обычно
`~1.5`) — расхождение в пределах 1-2% нормально (реальная поза Idle чуть
компактнее идеальной прямой стойки), расхождение на 10%+ значит где-то
всё ещё меряется не та поза.

## Енот: перенос по проверенной схеме — сырой Blender-файл + перенос недостающих полей

Применили процесс из чек-листа выше (см. "📋 ПРОЦЕСС") впервые на еноте.
Правка в Blender: хвост **переподключен весами** к одной кости `Hips`
(вся геометрия хвоста, ранее размазанная по нескольким костям, теперь
100% привязана к `Hips`) — сама длина/геометрия хвоста не менялась, это
чисто skin weight правка, аналог того, что раньше было сделано рантайм-
патчем `RACCOON_TAIL_FIX_RULES`, но теперь зафиксировано в самом файле.
Хвост крепится именно к `Hips`, потому что физически лежит у основания
спины, близко к тазу — в отличие от белки, чей хвост загнут вверх к
плечу и поэтому крепился к `Spine2`.

**Перенос выполнен программно** (бинарный FBX read/write, побайтовая
проверка round-trip перед операцией — 0 расхождений на тестовой
сериализации): взят сырой Blender-экспорт енота целиком (геометрия, веса,
материал, текстура — не тронуты), из чистого источника (прежний
`Breathing_Idle.fbx` енота, никогда не проходивший через Blender)
перенесены: анимация (`AnimationStack`/`AnimationLayer`/
`AnimationCurveNode`/`AnimationCurve`, с переподключением на кости
сырого файла по имени — ID костей у Blender-файла свои, пришлось
сопоставлять по имени, не по числовому ID), `PreRotation`+
`RotationActive` по каждой кости, `UnitScaleFactor`, 6 legacy-свойств
материала.

**Проверка — восемь пунктов:**
```
Геометрия (Vertices+PolygonVertexIndex): идентична сырому файлу
Deformer-веса: идентичны сырому файлу
Вершин без веса: 0 / 6305
Вершин с перевесом (>1.05): 0
PreRotation: 23/26 костей (столько же, сколько было у белки)
Кривых анимации: 123 = 123 (полное совпадение с чистым источником)
UnitScaleFactor: 100.0
Материал: все 6 legacy-свойств перенесены
Текстура: валидный JPEG, 581104 байт, встроена
```

**Важный нюанс для следующего раза (стоило времени на отладку):** первая
версия самодельного FBX-писателя (бинарная сериализация) записывала все
массивы данных (координаты вершин, кривые анимации) БЕЗ сжатия — файл
раздулся почти в 2 раза (1.48 МБ → 2.87 МБ) по сравнению с оригиналом,
хотя содержимое было идентичным. Оригинальные FBX используют zlib для
массивов длиннее ~128 байт. Добавили сжатие в писатель (`zlib.compress`,
уровень 6, порог 128 байт) — итоговый файл вернулся к нормальному весу
(1.49 МБ, сопоставимо с исходным чистым файлом енота 1.48 МБ).
Round-trip (parse → write → re-parse, побайтовое сравнение всех узлов и
свойств) проверялся ДО и ПОСЛЕ добавления сжатия — 0 расхождений в обоих
случаях, сжатие не влияет на корректность, только на итоговый размер
файла.

**Рантайм-патч для енота отключён** — `tailFixRules: []` в `CHARACTERS.
raccoon` (`main.js`), был `RACCOON_TAIL_FIX_RULES`. Импорт
`RACCOON_TAIL_FIX_RULES` в `main.js` убран как неиспользуемый (сама
функция и правило остались в `scene.js` нетронутыми — на случай отката).

**Про размер** — та же логика, что и у белки: масштаб теперь считается
через `measureAndApplyAutoScale()` после первого кадра Idle, а не по
статичной default-позе файла, так что скачка размера из-за разной позы
(T-поза vs впечённая Blender'ом поза Idle) для енота тоже не грозит —
фикс уже общий для обоих персонажей, ничего дополнительно чинить не
пришлось.

## Мобильная адаптация: "второй персонаж чуть выше" — рассинхрон canvas-слоёв при layout-изменениях

Замечено на мобильном после добавления `#track-name-mobile` (название
трека между сценой и панелью персонажей): когда там появляется текст,
эффект размытия контура персонажа (см. запись про edge-blur выше) начал
рисовать как будто второго персонажа, чуть смещённого вверх.

**Диагностика цифрами (не гадание) подтвердила механизм:**
```
ДО:    scene-container 248×321    renderer buffer 248×321   renderer displayed 248×321
ПОСЛЕ: scene-container 248×304.86 renderer buffer 248×321   renderer displayed 248×321
```
`#app` — flex-колонка, `#scene-container` делит высоту с соседями.
Когда в `#track-name-mobile` появляется текст, сам контейнер сцены
честно становится ниже — но WebGL-канвас нет. Причина:
`renderer.setSize()` в Three.js прописывает `style.width`/`style.height`
канваса **инлайн-стилем в пикселях**, не через `%` — побеждает любой
CSS. `resize()` (который заново вызывает `renderer.setSize()`) висел
только на `window.addEventListener("resize", ...)` — нативном событии
изменения размера ОКНА, а изменение размера СОСЕДНЕГО элемента (текст
появился в `#track-name-mobile`) такое событие не порождает вообще.
Итог: WebGL-канвас застревал на старом (большем) размере, торчал ниже
своего контейнера и обрезался через `overflow: hidden` (тот самый,
добавленный ради масштабирования волны, см. выше) — а canvas размытия
контура и canvas волны стилизованы через CSS `width:100%; height:100%`
(не инлайн), поэтому честно сжимались вместе с контейнером. Два слоя
одного и того же кадра персонажа рассинхронизировались по масштабу —
отсюда и "второй персонаж чуть выше".

**Фикс — `ResizeObserver` вместо (точнее, в дополнение к) `window
resize`.** И в `scene.js` (WebGL-канвас), и в `soundWave.js` (canvas
волны) теперь `new ResizeObserver(resize).observe(container)` —
реагирует на ЛЮБОЕ изменение размера самого `#scene-container`,
независимо от причины (не только реальный ресайз окна браузера, но и
любые будущие изменения разметки соседних элементов). Универсальный
фикс — не понадобится точечно вызывать `resize()` вручную после
КАЖДОГО нового элемента, который потенциально может повлиять на layout
сцены.

## Sound Wave — цветной столбчатый эквалайзер на фоне, реагирует на музыку

**История:** первая версия была волнистым кольцом вокруг персонажей
(`js/soundCircleWave.js`) — визуально оказалась "скучной", заменена на
крупный цветной столбчатый эквалайзер во всю ширину экрана
(`js/soundWave.js`), по образцу референсов (яркие вертикальные столбики,
зеркальные вверх/вниз от центра, градиент красный→оранжевый→жёлтый→
розовый→фиолетовый→синий→голубой слева направо). Тот же принцип
разделения слоёв, что и у остальных аудио-модулей — ничего не знает про
Three.js, только 2D canvas + числа от `AudioAnalyzer`.

**Два реальных бага при первой версии (кольцо было не видно вообще),
стоит помнить на будущее при похожей 2D-поверх-WebGL вёрстке:**
1. `renderer.setClearAlpha(0)` — `alpha: true` в конструкторе
   `WebGLRenderer` включает только ТЕХНИЧЕСКУЮ поддержку прозрачности у
   канваса; сам рендерер всё равно чистит кадр непрозрачным по
   умолчанию (`clearAlpha=1`), пока не сказать явно иначе.
2. Отрицательный `z-index` ненадёжен, если ближайший позиционированный
   родитель НЕ создаёт свой stacking context (`position:relative` без
   явного `z-index` — недостаточно) — элемент может "провалиться" ниже
   вообще всей страницы (у `html, body` тут был свой непрозрачный фон),
   а не просто ниже соседнего канваса. Фикс — два независимых момента
   вместе: (a) `#scene-container { isolation: isolate; }` в `style.css`,
   явно создаёт stacking context; (b) оба канваса сравниваются
   НЕОТРИЦАТЕЛЬНЫМИ z-index напрямую друг с другом — WebGL-канвас
   получает явные `position:relative; z-index:1` в `scene.js` сразу
   после `container.appendChild()`, звуковой canvas — `z-index:0`.

**Спектр по полосам, не 3 усреднённых диапазона.** `AudioAnalyzer` раньше
отдавал только `bass`/`mid`/`treble` (агрегаты по широким диапазонам —
достаточно для камеры/персонажей, но не для полноценного эквалайзера).
Добавлен `getSpectrumBars(barCount, maxHz)` — N полос с логарифмическим
шагом по частоте (20Hz..maxHz; линейная шкала на слух/на глаз выглядит
неестественно — почти весь бас попадает в первые несколько полос, а
все "интересные" средние/высокие частоты сжимаются в последние
пиксели). ВАЖНО: переиспользует `freqData`, уже считанный в этом же
кадре внутри `getFeatures()` — вызывать сразу после него, не раньше
(отдельного `getByteFrequencyData()` внутри `getSpectrumBars` нет).

**Как рисуется:** 56 столбиков (`BAR_COUNT`), зеркально вверх/вниз от
горизонтальной центральной линии, скруглённые углы (`roundRect`), общий
`fillStyle` — один canvas-градиент во всю ширину (красится сразу всё
разом, не поштучно на столбик). Каждый столбик сглаживается ЭКСПОНЕНЦИАЛЬНО
и НЕЗАВИСИМО от остальных (`BAR_SMOOTHING_TAU=0.09с` — заметно быстрее,
чем у камеры, эквалайзер должен визуально "дёргаться" живее). Минимальная
высота столбика (`MIN_BAR_HEIGHT_PX`) — не исчезают в ноль даже в полной
тишине, маленькая "живая" черта. Сильный бит — короткий общий "punch"
всех столбиков разом (`beatPunch`, экспоненциальное затухание). Холостой
режим (музыка не играет) — медленная бегущая синусоидальная волна по
столбикам вместо резкой заморозки.

Резайз обрабатывается независимо (свой `window.addEventListener("resize")`
внутри модуля, не завязан на `resize()` из `scene.js`).

**Донастройка после первого показа ("не вау-эффект, скучно"):** первая
версия оказалась предсказуемой — левые (басовые) столбики всегда выше
правых (высокочастотных) независимо от трека, гладкая огибающая без
"шума" между соседними столбиками. Два фикса:
1. `getSpectrumBars()` в `audioAnalyzer.js` — компенсация естественного
   спада энергии с частотой (`gain = (centerHz/200)^0.55`), музыка почти
   всегда громче в басу, чем в верхах, без компенсации это доминирует
   всегда и везде.
2. `soundWave.js` — фиксированный (не на каждый кадр) псевдослучайный
   `barJitterGain` на каждый столбик (`JAGGEDNESS_STRENGTH=0.55`) — даёт
   "рядом с высоким может стоять низкий", плюс лёгкое центрирование
   (`barCenterWeight`, гауссиана) — пик визуально чаще ближе к середине.

**Live-панель настройки (временно спрятана, не удалена)** — четыре
ползунка (высота/масштаб, количество столбиков, толщина столбиков,
длина волны сжатием группы целиком — НЕ через количество столбиков,
плюс размытие) с выводом текущего значения, дёргают `set*`-функции
`soundWave.js` без перезагрузки. `panel.style.display = "none"` в конце
IIFE — код рабочий, если понадобится ещё раз подбирать вид.

**Три режима по кнопке (иконка — `assets/ui/wave-mode-icon.jpg`,
пользовательский референс-скриншот), справа от кнопки умной камеры,
цикл по клику:** `blur` (размытие, дефолт при загрузке) → `normal`
(чёткие столбики) → `off` (слой скрыт целиком, `soundWave.setVisible
(false)`, обычный экран как до этой фичи) → снова `blur`. Значения
каждого режима (`MODE_SETTINGS` в `main.js`) — присланы пользователем
через ту самую live-панель (не гадание, конкретные подобранные цифры):

```
blur:   высота=20% столбики=50 толщина=20% длина=70% размытие=50px
normal: высота=20% столбики=50 толщина=50% длина=70% размытие=0px
```

## Камера: ручное вращение, "умная камера" (единственная кнопка)

**Ручное вращение** — `OrbitControls` (были только за `?debug`, теперь
включены всегда). Панорамирование выключено (`enablePan=false`, нельзя
"укатить" камеру и потерять персонажей), только вращение и зум.
Ограничение по вертикали: сверху можно смотреть вплоть до прямо сверху
вниз (`minPolarAngle=0`), снизу — не ниже уровня глаз минус запас (см.
ниже про 13°/−7°).

**Кнопка `🏠` (плавный возврат за 0.8с) — убрана полностью**, вместе со
своим механизмом (`cameraResetActive`/`CAMERA_RESET_DURATION` и т.д.).
Стала не нужна, когда сама умная камера научилась плавно ехать домой
при выключении (см. `smartCameraReturningHome` ниже) — держать в UI два
разных способа "вернуть камеру", ведущих себя по-разному (0.8с твин
против экспоненциального ease), только путало. Осталась одна кнопка —
`🎥`.

**Кнопка `🎥` — "умная камера".** Не полный оборот по кругу, а конечный
автомат из двух режимов:

- **`sweep` (качели)** — по горизонтали чистая синусоида: центр→+70°→
  центр→−70°→центр→повтор (140° всего). Скорость одного прохода — база
  ~20с (сознательно замедлено на 20% от исходных ~16с), слегка
  ускоряется на пиках `intensity` (та же величина, на которую уже
  реагируют танцующие персонажи — не BPM/темп трека, а сглаженный
  уровень "энергичности" звука здесь и сейчас). Одновременно
  несимметричная волна по вертикали: старт с уровня глаз (0°), вверх до
  `+13°`, вниз до `−7°` ниже глаз, и по кругу — 2 волны за один
  горизонтальный проход. `SMART_CAMERA_VERTICAL_UP_DEG`/`_DOWN_DEG`
  задают эти пределы, `controls.maxPolarAngle` в них же завязан — ручное
  вращение мышью может заходить настолько же ниже уровня глаз, насколько
  и умная камера.
- **`spin` (полный оборот)** — после `SMART_CAMERA_SWEEPS_BEFORE_SPIN`
  (сейчас 2) проходов качелей — один полный оборот на 360° за
  **фиксированные 4 секунды**, НЕ зависящие от intensity (в отличие от
  качелей). Та же волна 15°/−7° (сейчас 13°/−7°), но ровно один раз за
  весь оборот. Направление чередуется: первый оборот влево, следующий
  вправо, и так далее (`smartCameraSpinDirection *= -1` при завершении
  оборота). Переключение между режимами происходит именно в момент, где
  камера и так на центре (конец качелей = центр по конструкции синуса,
  конец оборота = центр, т.к. это полные 360°) — без видимого скачка.

Плюс лёгкий "пульс" приближения через `camera.fov` (не через позицию —
не конфликтует с математикой `OrbitControls`) на сильных битах,
независимо от режима.

**Возврат камеры домой во время Idle — не только на паузе.** Первая
версия смотрела только на факт "играет ли аудио" (`!player.isPaused()`)
— и не замечала случай, когда персонаж уходит в Breathing Idle **посреди
играющего трека** (музыка на секунду стихла, `danceBag` выбрал паузу
и т.п.) — камера в этот момент продолжала крутить качели/оборот, хотя
никто не танцевал. Исправлено: проверка идёт по реальному состоянию
анимации персонажа (`animController.getCurrent() !== "idle"` хотя бы у
одного активного персонажа), а не по факту воспроизведения звука. Логика
возврата вынесена в отдельную `driveCameraHome(delta)` — используется и
тут, и в общем случае "музыка вообще не играет" (пауза/конец трека/ещё
не запущена), без дублирования кода. Экспоненциальный ease (не линейный
lerp с фиксированной длительностью) — чем дольше длится Idle, тем ближе
к дому, само "застывает", когда разница станет незаметной. Фаза качелей/
оборота при возврате сбрасывается — следующий заход умной камеры после
Idle начинается заново с центра/качелей, а не с середины того, на чём
остановились.

**Возврат домой и при выключении умной камеры (не только на Idle).**
Раньше выключение кнопкой `🎥` просто замирало камеру там, где она была
в этот момент. Теперь `setSmartCameraEnabled(false)` ставит флаг
`smartCameraReturningHome = true`, и `renderLoop` продолжает вызывать
тот же `driveCameraHome()` (тот же экспоненциальный ease, что и на
Idle/паузе — не твин кнопки `🏠`, которой больше нет) до тех пор, пока
камера не подлетит ближе `SMART_CAMERA_HOME_SNAP_DISTANCE` (1см) к
исходной позиции — после этого флаг сбрасывается, и управление
возвращается обычному ручному вращению. Работает независимо от того,
играет музыка в этот момент или нет — источник истины "нужно ли ехать
домой" теперь три независимых состояния: `smartCameraEnabled` (крутить
качели/оборот), `smartCameraReturningHome` (едем домой после
выключения), и ничего из этого (обычное ручное управление).

По пути ещё завели свой явный флаг `musicIsPlaying` (управляется
вручную в `onPlay`/`onPause`/`onEnded`, не полагается на
`audio.paused`) — изначально задумывался как фикс другого бага
(оказалось, что тот баг был придуман, не реальный: `onPause` и так
надёжно срабатывает и при естественном окончании трека), но сам флаг
остался — он корректен и достаточно однозначен как источник истины,
вреда не приносит, дублирующие вызовы `ctrl.play("idle")` в `onPause`+
`onEnded` безопасны (в `animationController.play()` есть защита: если
запрошенный клип уже играет — no-op).

**Прочее в этом же заходе:** цвет фона сцены — `#0d0d0d` (был
`0x15171c`). Временный canvas-пикер фона (свой градиент вместо
нативного `<input type="color">`, чтобы не показывались системные поля
RGB/HSL) добавлялся, а затем убран по запросу — из UI остались только
кнопки `🎥`/`🏠`. Расстояние между персонажами в Duet
(`computeOffsets` spacing) — было `1.8`, стало `1.3` через несколько
итераций (1.8→1.2→1.3).

## Duet: компенсация перспективного разворота персонажей

Замечено (одинаково для обоих персонажей, не только у одного): в Duet
каждый персонаж выглядел слегка развёрнутым в сторону от камеры, хотя в
соло стоял строго анфас. Причина не в скелете/анимации — камера всегда
смотрит в одну и ту же точку `(0, 0.95, 0)` (общий центр сцены), а сами
персонажи в Duet раздвинуты от центра (`computeOffsets`, ±0.9 при двух
персонажах). Раз камера целится не персонально в каждого, а в среднюю
точку между ними — оба физически видны под углом
`arctan(0.9 / 5.0) ≈ 10.2°`, зеркально друг к другу. Чистая перспектива
одной фиксированной камеры на нескольких разнесённых персонажей, не баг.

**Фикс** — `faceCameraCompensated(model, offsetX, cameraZ)` в `scene.js`:
довора­чивает модель вокруг Y на компенсирующий угол
(`Math.atan2(-offsetX, cameraZ)`), чтобы она снова смотрела точно на
камеру, как в соло. При `offsetX=0` угол компенсации нулевой — соло не
меняется. Вызывается в двух местах в `main.js`: сразу после
`groundAndCenterModel()` при первой загрузке персонажа (ДО
`captureBasePose()`, чтобы процедурные покачивания считались уже от
скорректированной ориентации), и повторно при смене `offsetX`
(переключение соло↔Duet для уже загруженного персонажа).

**Отдельная поправка после теста:** первая версия фикса разворачивала
только визуально (`model.rotation.y`), но не обновляла `baseRotY` внутри
`animationController.js` — а именно к этому углу откатывает персонажа
`resetPose()` на паузе. `baseRotY` фиксируется через `captureBasePose()`,
которая изначально вызывалась только один раз, при самой первой загрузке
слота. Если персонаж сперва грузится в соло (offsetX=0, `baseRotY=0`), а
потом добавляется в Duet — визуальный разворот применяется, но на паузе
`resetPose()` откатывал его обратно к старому `baseRotY=0`, и персонаж
на паузе снова "поворачивался". Персонажей, которые сразу грузятся в
Duet (не переключаются туда из уже загруженного соло), это не касалось —
у них `captureBasePose()` с самого начала фиксировал уже правильный угол.
Фикс: `captureBasePose()` вызывается заново сразу после
`faceCameraCompensated()` там же, где обновляется `offsetX` при смене
состава — не только при первой загрузке.

## Список танцев урезан + файлы облегчены (вырезан лишний skin)

**Список танцев** в `CHARACTERS.*.animationFiles` (`main.js`) сокращён по
явному запросу — убраны конкретные клипы у белки (`hiphop_1`,
`uprock_brooklyn`, `maraschino`) и у енота (`hiphop_1`, `hiphop_2`,
`hiphop_3`, `hiphop_4`, `hiphop_5`, `hiphop_7`, `silly_1`, `shuffle`,
`twerk`). `DANCE_LABELS` не трогали — там лишние записи безвредны (это
просто словарь подписей по имени клипа, кнопки строятся из
`animationFiles`, а не из `DANCE_LABELS`).

**Обнаружено:** каждый танцевальный FBX при скачивании с Mixamo
качался с галочкой "with skin" — то есть нёс полную копию геометрии,
скина, материала и текстуры персонажа внутри себя, хотя
`loadAnimationClipsFBX()` в `scene.js` читает из этих файлов **только**
`fbx.animations` — кривые движения костей. Меш/веса/материал из
танцевальных файлов никогда не используются и не отображаются: то, что
рисуется на экране, всегда берётся из `Breathing_Idle.fbx` персонажа —
единственного файла, где skin реально нужен.

**Сделано:**
1. С диска удалены файлы, которых больше нет в списке `animationFiles`
   (мёртвый груз от предыдущей правки списка танцев).
2. Из оставшихся 18 файлов (9 у белки + 8 у енота, `loading_pose.fbx`
   тоже сюда попал) программно вырезаны узлы `Geometry`, `Material`,
   `Texture`, `Video`, `Deformer`, `Pose` и все связанные с ними
   `Connections` — тем же бинарным read/write-инструментом, что и для
   переноса весов енота (см. выше). `Model` (кости/`PreRotation`,
   нужны для имён костей/треков анимации) и `AnimationStack`/
   `AnimationLayer`/`AnimationCurveNode`/`AnimationCurve` (сама
   анимация) оставлены нетронутыми.
3. Проверено: у всех 18 файлов после правки `Model=26`, `AnimCurve=123`
   (совпадает с ожидаемым), `Geometry`/`Material` отсутствуют, ключевые
   кадры (`KeyTime`/`KeyValueFloat`) не пустые — данные реальные, не
   только структура.

**Итог:** `22.10 МБ → 7.18 МБ` только на танцевальных файлах (сжатие
~в 3 раза), без какой-либо потери функциональности — анимации
проигрываются ровно как раньше, поскольку код никогда не читал
вырезанные данные.

**На будущее:** при скачивании новых танцев с Mixamo — галочку "with
skin" ставить **только** для файла-персонажа (`Breathing_Idle.fbx`), для
всех танцевальных клипов её нужно снимать. Так новые файлы сразу
придут в разы легче, без необходимости прогонять их через этот же
скрипт постфактум.

**Баг сразу после вырезания (важно на будущее для похожих скриптов):**
первая версия скрипта вырезала объекты (`Geometry`/`Material`/...) из
`Objects` и связанные `Connections`, но не трогала `Definitions` —
отдельную секцию-"паспорт" в начале FBX, которая заранее объявляет,
сколько объектов каждого типа ожидать (`ObjectType: Material, Count: 1`
и общий суммарный `Count`). Она осталась врать, что материал/геометрия/
деформеры всё ещё есть, хотя их уже вырезали. Из-за этого `FBXLoader`
переставал нормально грузить файлы — пропадали кнопки танцев, персонажи
оставались в Idle. Фикс: после вырезания объектов пересчитывать
`Definitions` — убирать `ObjectType`-записи для типов, которых больше
нет в `Objects`, и пересчитывать общий `Count` как реальное число
оставшихся объектов. Общее правило на будущее: при хирургии бинарного
FBX (вырезание/перенос узлов) `Definitions` — не декоративная секция,
её нужно синхронизировать с `Objects` в паре, иначе лоадер молча
ломается без явной ошибки в консоли.

**Второй баг после того же вырезания (настоящая причина "кнопки танцев
пропали"):** `Definitions` была не единственной проблемой. У каждого
файла остался ОДИН лишний `Model`-узел — не кость, а сам контейнер меша
(`tripo_node_...`, подтип `'Mesh'` в его собственных свойствах, третье
поле). При вырезании убрали саму `Geometry`, но не тронули этот `Model`
— а `FBXLoader` (`FBXTreeParser.parseModels` → `createMesh`) выбирает,
что делать с каждым `Model`, по подтипу в его собственных свойствах
(`'Mesh'` vs `'LimbNode'` vs `'Root'`/`'Null'`), а не по факту наличия
подключённой `Geometry` в момент парсинга. Раз подтип остался `'Mesh'`
— лоадер всё равно пытался вызвать `createMesh()`, а внутри падал с
`TypeError: Cannot read properties of null (reading 'attributes')`,
потому что геометрии для этого меша уже не существовало. Ошибка ломала
`loadAnimationClipsFBX()` целиком → пустой список анимаций → кнопки
танцев не появлялись, персонаж оставался в Idle.

Фикс: помимо `Geometry`/`Material`/`Texture`/`Video`/`Deformer`/`Pose`,
из `Objects` дополнительно убирается сам `Model`, у которого третье
свойство (подтип) равно `'Mesh'` — вместе с его `Connections` и
уменьшением счётчика `Model` в `Definitions` на единицу. У всех 18
файлов было ровно по одному такому узлу. После фикса: `Models=25`
(только кости, `LimbNode`), `Mesh-type Models=0`, `AnimCurve=123` — без
изменений. Итоговый вес: `animations-fbx` 4.1 МБ, `animations-fbx-
raccoon` 3.1 МБ (было 22.1 МБ суммарно на оба до всей операции).

**Общее правило на будущее, если будем резать FBX подобным образом
снова:** при удалении объекта (`Geometry` и т.п.) недостаточно убрать
только сам объект и прямые связи на него — нужно проверить, не
"осиротеет" ли какой-то `Model`, чей единственный смысл существования
был в этом объекте (подтип `'Mesh'` без геометрии не имеет смысла).
Безопаснее всего проверять по подтипу узла (`props[2][1]`), а не только
по наличию/отсутствию связей в `Connections`.

## Эксперимент: поза вместо спиннера при загрузке (шестьдесят второй репорт)

По запросу — вместо голого спиннера персонаж замирает в присланной позе
(`Female_Dance_Pose.fbx` → `assets/animations-fbx/loading_pose.fbx`), пока
остальные танцы догружаются в фоне. Файл — не полноценный персонаж, а
анимация-поза под тот же `mixamorig`-скелет (2 ключевых кадра, встроенный
меш отброшен, как и у обычных танцевальных клипов).

**Как работает**: загружается в приоритете сразу после самого персонажа
(маленький файл, быстро) — сразу как готов, mixer прыгает на финальный
кадр позы, спиннер прячется раньше обычного. Поза может сильно отличаться
от Idle по стойке — грунтовка/центрирование пересчитаны заново именно под
неё, иначе персонаж мог бы "парить" на превью.

**Защита от протечки в реальный список танцев** — добавил `NON_DANCE_CLIPS`
(набор служебных имён клипов: `idle`, `loading_pose`), используется и в
мешке ротации танцев, и в списке кнопок UI-панели. Без этого поза для
загрузки могла бы случайно попасть в обычную ротацию как настоящий танец.

**Легко откатить** — `LOADING_POSE_URL` в `main.js` в одну константу,
поставить в `null` вернёт обычный спиннер без изменений где-либо ещё.

## Нашли и убрали лишний объектный масштаб — размер тоже почини­н (семьдесят третий репорт)

После подтверждения цвета спросили про размер — Stanislav подтвердил, что
реально видит разницу (текущая белка немного крупнее). Проверил все
факторы разом: `UnitScaleFactor` совпадал (100.0 в обоих), сырые
координаты вершин идентичны байт-в-байт — но нашёл третий, отдельный
фактор, который раньше не проверялся: у корневых объектов (`Armature` и
сам меш `tripo_node_17231253`) в текущем файле стоял явный **`Lcl Scaling:
100,100,100`**, а в чистом источнике этого свойства не было вообще
(дефолт 1,1,1). Это отдельный от `UnitScaleFactor` механизм — Blender
записал его при экспорте, у отдельных костей (Hips, Spine и т.д.) такого
масштаба не было, только на корневых объектах.

Теоретически наша система авто-масштаба (измеряет реальный рост после
загрузки, не полагается на абсолютные единицы) должна была это
компенсировать сама — но раз Stanislav подтвердил реальную видимую
разницу, не стал спорить с практикой ради теории. Убрал эти два свойства
целиком, приведя к тому же виду, что у чистого источника.

**Проверка**: веса вершин не тронуты (0 расхождений), масштаб корневых
объектов теперь точно совпадает с чистым источником (оба без явного
масштаба), анимация/текстура/материал (включая недавно почини­нный
`Opacity`) на месте.

## Найдена и почини­на настоящая причина "светлой" белки (семьдесят второй репорт)

Проверил две альтернативные гипотезы Stanislav (настройки Blender при

## Основание хвоста "плавало" — неверный якорь, Spine2 вместо Hips (шестьдесят восьмой репорт, не помогло)

физически ближе к этой точке, `Spine2` — далеко (через всю спину), отсюда
разрыв/"плавание".

правки) и переставил именно их с `Spine2` на `Hips` — жёстко, без блендинга,

## Два отдельных фикса разом — рантайм-код и последний остаток хвоста (шестьдесят седьмой репорт)

Оба симптома ("и с коленями, и хвост растягивается") оказались реальными,
но с разными причинами.

**1) Рантайм-код применялся не к тому персонажу.** Правило
`{ Hips, UpLeg }` в `TAIL_FIX_RULES` было задумано только для енота (у
него хвост никогда не чинился на уровне файла), но применялось **ко всем**

конфликтуя с уже аккуратно перенесёнными файловыми весами. Сделал правило
явно per-character: `loadCharacterFBX()` в `scene.js` теперь принимает
`tailFixRules` параметром, а не берёт глобальную константу — передаётся
только для енота (`RACCOON_TAIL_FIX_RULES`), белка больше не получает
никакого рантайм-патча вообще.

**2) Последний непочиненный остаток хвоста.** После отключения рантайм-
правила стало видно то, что оно раньше маскировало: **80 вершин** у
самого основания хвоста были смешаны между `Hips` и `LeftUpLeg` — эта
зона никогда не чинилась на уровне файла, только рантайм-патчем. Перенёс

зоны хвоста (384 вершины — настоящий сустав бедро-таз) осталось нетронутым.

**Итог**: хвост теперь на 100% чисто на `Spine2` по всей своей длине (0
исключений при широкой проверке), без остатка и без зависимости от
рантайм-кода — вся починка отныне живёт в самом файле.

## Багфиксы после пятого репорта (белки не видно + пауза)

**Белки не видно на экране.** По твоим скриншотам консоли — реальных ошибок
загрузки нет (13 warning про "more than 4 skinning weights" безобидны, Three.js
сам их обрезает; 404 на favicon.ico вообще не о нашем коде). Раз плейсхолдер
пропадал — модель технически грузилась, просто оказывалась не того размера
или не в кадре.

Вместо того чтобы дальше подбирать `scale` вручную — переписал
`loadCharacterFBX` на **автоматическую подгонку**: теперь после загрузки
меряется реальный bounding box модели и сам вычисляется коэффициент, чтобы
персонаж стал ростом `targetHeight` (по умолчанию 1.5м — белка поменьше
человека), плюс модель автоматически ставится на пол (низшая точка меша →
y=0), независимо от того, где был исходный pivot в файле. Это устраняет
проблему в принципе, а не только для этой конкретной белки — сработает для
любого будущего кастомного персонажа с непредсказуемым масштабом экспорта.

В консоли теперь будет строка вида:
```
[scene] FBX персонаж: исходный рост 87.234 ед. → scale=0.01719 → итоговый размер 1.02 x 1.50 x 1.83 м, ступни на y=0.000
```

## Проверка

Открой заново — белка должна появиться сама, без ручной подстройки
масштаба. Если всё ещё не видно — открой вкладку **Console** (не Elements!)
в devtools и пришли именно её содержимое, особенно эту строку про
"FBX персонаж" — по ней сразу будет видно, в чём дело (например, если
исходный рост окажется 0 или отрицательным — значит, проблема в самой
геометрии/скелете модели, не в масштабе).

## Багфиксы после шестого репорта (телепорт в первую секунду + обрыв танца на середине)

**Телепорт в первую секунду.** Постановка на пол/центрирование считались по
статичной bind-позе персонажа — ДО того, как реально начала играть Idle
анимация. Как только `mixer` делал первый шаг, корневая кость (Hips)
сдвигалась туда, куда её ведёт сама анимация — а поза уже "приклеена" к
координатам, посчитанным для другой, стартовой позиции. Отсюда видимый
скачок. Исправлено: `groundAndCenterModel()` теперь вызывается ПОСЛЕ
`mixer.update(0)` с уже играющим Idle — меряем и ставим на место реальную
первую анимированную позу, а не бинд-позу. Заодно поправил
`animationController` — `baseY`/`baseRotY` (база для процедурного
приседания/покачивания) фиксировались в момент создания controller'а, то
есть тоже до постановки на пол; добавил `captureBasePose()`, вызывается
следом за `groundAndCenterModel()`.

**Обрыв движения на середине жеста при смене танца.** Раньше ротация
основного танца переключалась мгновенно по истечении таймера
(`danceRotateSeconds`), не глядя на то, что в этот момент реально
происходит на экране — отсюда "рука поднята для одного движения, и тут
резко переход на другое с опущенной". Исправлено: по истечении таймера
следующий танец не запускается сразу, а ставится "в очередь"
(`pendingMainDance`). Каждый кадр проверяется, сколько времени осталось до
конца текущего цикла (`currentAction.time % duration`), и переключение
происходит только в последние `danceSwitchLeadTime` (0.35с) — то есть
crossFade стартует ровно к моменту, когда цикл и так должен был начаться
заново. Жест успевает довестись до конца, следующий танец подхватывает с
чистого начала, а не обрубка.

## Проверка

Персонаж должен появляться на месте сразу, без прыжка в первую секунду.
Смена танцев на активных участках — только в моменты, когда предыдущее
движение уже логически завершилось (не обязательно ровно на 9-й секунде —
может чуть раньше/позже, в пределах текущего цикла).

## Багфиксы после седьмого репорта (T-поза висела всю загрузку танцев + рывки в такт биту)

**T-поза/не по центру ДО загрузки трека, потом снап в центр.** Дело было не
в рендеринге, а в порядке загрузки. `mixer.update(0)` и постановка на
пол/центр раньше ждали, пока догрузятся **ВСЕ 13 файлов** (`await
Promise.all(...)` для 12 танцев) — и только после этого персонаж
корректировался. Пока качались 12 файлов с танцами (секунда-другая),
на сцене честно висела необработанная T-поза не по центру. Исправлено:
`animController` создаётся, `play("idle")`, `mixer.update(0)`,
`groundAndCenterModel()` — всё это теперь происходит **сразу после
собственного файла персонажа**, до того как вообще начинается загрузка
остальных 12 танцев. Танцы подгружаются в фоне через `addClips()` — персонаж
уже стоит на месте и дышит, пока они докачиваются.

**Рывки "в такт биту" — реальный баг, не показалось.** `timeScale` (скорость
проигрывания текущего танца) пересчитывался **каждый кадр** напрямую из
сырого `intensity` — а intensity дёргается вместе с каждым басовым ударом.
На практике это означало: рука поднимается в среднем темпе — прилетает бас
— `intensity` скачком растёт — `timeScale` уже играющего действия скачком
меняется — движение визуально "спотыкается"/ускоряется посреди жеста ровно
в момент удара. Никакой логики "успеть добить жест к биту" в коде не было —
это была чистая математика: скорость слишком резко следовала за шумным
сигналом. Исправлено:
- `timeScale` теперь сглаживается ОТДЕЛЬНО и МЕДЛЕННО (`timeScaleSmoothingTau
  = 1.8` секунды) — не мгновенно из сырого intensity, а через экспоненциальное
  скольжение с постоянной времени почти 2 секунды. Скорость танца теперь
  плывёт за общим настроением трека (тихий куплет → чуть медленнее, плотный
  припев → чуть быстрее), а не дёргается на каждый отдельный удар
- Сужен сам диапазон скорости: `maxTimeScaleBonus` 0.65 → 0.4 (было
  0.85x-1.5x, стало 0.85x-1.25x) — даже сглаженные изменения теперь мягче

Разделение осталось прежним и тем, что тебе понравилось: переход между
tier'ами (calm/light/active, то есть заметный переход "музыка стихла →
персонаж встал на Idle") остаётся быстрым и отзывчивым — плавным
crossFade, но БЕЗ полуторасекундной задержки. Задержка применяется только к
скорости воспроизведения ВНУТРИ уже выбранного танца, не к самому решению
"пора сменить состояние".

## Проверка

Персонаж должен появляться на месте практически сразу — без T-позы,
провисающей на секунду-другую, без снапа в центр. Во время танца скорость
движений должна ощущаться как плавный "разгон/торможение" по настроению
трека, а не как рывки синхронно с каждым битом. Резкая смена
тихо↔громко (например, вступление → бочка) должна по-прежнему быстро
переключать между Idle и танцем.

## Багфиксы после восьмого репорта (кнопка Beat не влияла на рывки — и это подсказало настоящую причину)

Кнопку проверил — подключена правильно, честно гасит и позиционный "хлоп",
и акцентные клипы. Но раз рывки оставались **и при выключенной кнопке**,
это доказало, что дело не в ней и не в акцентах — моя гипотеза из прошлого
шага была неверной. Зато сам факт помог найти настоящую причину.

**Реальная причина: процедурное приседание (`smoothedVisualBass`) вообще
не было завязано на кнопку Beat** — оно брало сырой `bass` каждый кадр
напрямую, в обход всего, что кнопка выключает. Плюс у него (и у intensity
в `audioAnalyzer.js`) сглаживание было "по кадрам" (`x = x*factor +
new*(1-factor)` без учёта `delta`), а не по времени — из-за этого реальная
скорость сглаживания зависела от FPS устройства и в целом была слишком
резкой. Тело буквально "подсаживалось" почти вслед за каждым сырым
колебанием баса — руки к этому моменту уже двигались гладко (после
прошлых фиксов), а корпус продолжал дёргаться отдельно от них, что и
читалось как общая "рваность" движения.

Исправлено — оба места переведены на сглаживание по ВРЕМЕНИ (экспоненциальное
скольжение с постоянной времени в секундах, не завязанное на FPS):
- `animationController.js`: `visualBassSmoothingTau = 0.3с` (было `0.75` за кадр)
- `audioAnalyzer.js`: `createIntensityTracker` → `smoothingTau = 0.35с` (было `0.85` за кадр)

Осталась в UI — гасит позиционный "хлоп" на beat и акцентные одноразовые

Движения корпуса (присед/покачивание) теперь должны быть заметно более

## Мешок раздавал "протухшие" отключённые танцы (восемнадцатый репорт)

**Баг: "выключил 10 из 12 кнопок — белка полпесни простояла в Idle".**
Причина в самом shuffle bag, не в логике переключения (та из прошлого
фикса работала верно). Мешок тасуется один раз и хранит уже готовую
перемешанную пачку; если пользователь выключает кнопку **после** того, как
мешок был перемешан, отключённое имя всё ещё физически сидит в этой пачке
— `next()` вытягивал его как обычно. Дальше срабатывала наша же страховка
из прошлого фикса ("этот танец отключён — откатываемся в idle") — и вместо
того чтобы просто вытянуть из мешка СЛЕДУЮЩИЙ валидный танец, персонаж
уходил в Idle. Чем больше кнопок выключено, тем больше шанс вытянуть
"протухшее" имя из уже готовой пачки — отсюда "полпесни в бризе" именно
при выключении большинства танцев.

Исправлено — `next()` теперь фильтрует мешок по АКТУАЛЬНОМУ списку
включённых прямо перед каждой раздачей (не только при полной пересдаче):
протухшие элементы просто вычищаются, и если после этого мешок опустел —
пересдаётся заново уже из живого списка. Раздаётся только то, что реально
включено на этот момент.

## Два бага: кнопки отключения танцев не работали + иконка Play не сбрасывалась (семнадцатый репорт)

**"Выключил все синие кнопки, а белка продолжает танцевать".** Причина —
`setDanceEnabled()` ставил замену "в очередь" (`pendingMainDance`) и ждал
конца текущего лупа, тем же механизмом, что и обычная фоновая ротация.
Для сознательного клика пользователя это неправильно — во-первых, эффект
ощутимо запаздывает (до конца текущего танца, это может быть много
секунд), во-вторых, если пользователь успевал выключить ещё несколько
кнопок подряд, `currentMainDance` мог вообще застрять на уже отключённом
танце навсегда — `hasClip()` проверял только "клип загружен", не "клип
включён", так что `play(currentMainDance, ...)` продолжал честно играть
уже отключённый танец бесконечно.

Исправлено:
- `setDanceEnabled()` теперь переключает **немедленно**, не через очередь —
  это осознанное действие пользователя, а не фоновый таймер, ждать конца
  лупа смысла нет
- Финальная проверка перед `play()` теперь смотрит не только `hasClip()`,
  но и `!disabledDances.has(currentMainDance)` — отключённый танец физически
  не может начать/продолжить играть, даже как страховка от других путей

**Иконка Play не сбрасывалась после загрузки нового трека.** Смена
`audio.src` на новый файл не всегда триггерит нативное DOM-событие
`'pause'`, даже если по факту воспроизведение остановлено — а наша иконка
обновлялась только по этому событию. Если выбрать новый трек во время
паузы старого, иконка Pause (❚❚) могла остаться висеть, хотя новый трек
ещё не запущен. Исправлено — сбрасываем иконку явно в обработчике выбора
файла, не полагаясь на браузерное событие.

## Проваливание всё ещё было — настоящая причина оказалась другой (двадцать четвёртый репорт)

Запас в 8мм (прошлый фикс) не помог — и по описанию стало понятно, почему:
проваливание проявлялось именно во время танца, а не на паузе и не на
Idle. Это совпадает не с "разницей между клипами", а с процедурным
**приседом от баса** (`squatAmount = 5см`) — на энергичных танцах бас
обычно громче, чем на спокойном Idle, приседание становится заметнее и с
лёгкостью перекрывает крошечный 8-миллиметровый запас. На паузе приседа
нет вообще (`resetPose()` его обнуляет), на Idle бас обычно тихий — вот
почему там всё было нормально.

Вместо того чтобы дальше подбирать запас "на глаз" — добавил жёсткий
клэмп: `model.position.y = Math.max(..., tuning.floorClampY)`. Присед (или
что угодно ещё, что может тянуть персонажа вниз) физически не может
утопить его ниже уровня пола, независимо от силы баса, разницы между
клипами или чего-либо ещё. Настраивается через
`jerrySlots.raccoon.animController.tuning.floorClampY`, если понадобится
подвинуть на конкретном персонаже.

(HTML, CSS, JS-подсчёт `loaded/total` по каждому файлу) — оставлен только
крутящийся спиннер, показывается/прячется по простому счётчику активных
загрузок (`activeLoadCount`), без процентов.

## Три доработки UI: порядок в дуэте, выход из дуэта, экран загрузки (пятьдесят седьмой репорт)

**1) Фиксированный порядок слева/направо.** Раньше позиция в сцене
считалась по порядку `activeCharacterIds` (порядку клика в пикере) — один
и тот же дуэт мог оказаться зеркальным в зависимости от того, кого
выбрали первым. Добавлен `CHARACTER_POSITION_ORDER = ["raccoon",
"squirrel"]` — офсеты теперь считаются по этому фиксированному порядку
(`getPositionOrder()`), а не по порядку выбора. Новых персонажей без
явного места в списке — в конец.

**2) Выход из дуэта обратно в соло.** Баг: кнопка подтверждения в пикере
требовала минимум 2 выбранных ВСЕГДА, даже при уменьшении уже
существующего дуэта — то есть из дуэта нельзя было вернуться к одному
персонажу никаким способом. Разделил логику: минимум 2 обязателен только
при свежем входе из соло (`activeCharacterIds.length === 1`, значит
холостой клик по 👯 без выбора кого-то ещё не должен ничего менять); если
же пикер открыт уже ИЗ дуэта (`activeCharacterIds.length >= 2`), разрешено
уменьшить состав хоть до 1 — это и есть единственный способ выйти обратно
в соло.

**3) Экран загрузки вместо синей капсулы.** Раньше персонаж проходил три
визуальные стадии: синяя placeholder-капсула → замёрзшая T-поза персонажа
→ через ~2с оживает в Idle. Капсула убрана из 3D-сцены совсем, заменена на
HTML/CSS-оверлей (`#scene-loading`) — спиннер + полоска прогресса,
которая растёт по мере догрузки каждого файла танца
(`beginLoadingTracking`/`stepLoadingTracking`/`endLoadingTracking` в
`main.js`). Оверлей прячется только когда персонаж ПОЛНОСТЬЮ готов —
Idle уже играет и все танцы догружены, кнопки отрисованы — то есть
пользователь видит: загрузка → сразу живой Idle, без замороженной
паузы между ними. Работает и для нескольких персонажей разом (Duet) —
прогресс считается по сумме "загружено/всего" по всем текущим загрузкам.

## Наконец нашли настоящую причину дыры на шее — это код, не файл (пятьдесят шестой репорт)

Stanislav был прав, что видел разницу — я был прав, что файлы идентичны.
Обе вещи правда одновременно: дело было в **коде**, не в файле.

Сравнил `scene.js` между архивами `ui-polish` (шея чистая) и
`waveform-hover` (шея с дефектом) — при абсолютно одинаковом FBX-файле.
Нашёл: в `waveform-hover` уже была функция `rigidifyContaminatedSkinWeights()`
с правилом:
```js
{ dominantHint: "Spine2", contaminantHints: ["LeftArm", "LeftShoulder", "Neck"] }
```

Это JS-код, который выполняется в браузере при КАЖДОЙ загрузке модели —
поверх уже загруженного меша, независимо от того, что записано в самом
файле. Правило гласило: "если у вершины есть вес и на Spine2, и на Neck
одновременно — жёстко присвоить её Spine2". У настоящей шеи на стыке с
корпусом обычно ЕСТЬ небольшая законная примесь Spine2 (для гладкого
сгиба) — правило рвало эту связь принудительно, создавая видимое
растяжение/тёмное пятно.

**Это объясняет, почему ничего не помогало последние несколько дней** —
я чинил веса в самом FBX-файле (Blender, потом мои переносы/склейки), а
этот рантайм-код продолжал портить их заново при каждой загрузке,
независимо от того, что было в файле.

Убрал это правило (и его зеркальную версию для RightArm/RightShoulder)
из `TAIL_FIX_RULES` — раз хвост белки теперь чинится на уровне самого
файла (аккуратный перенос весов, пятьдесят четвёртый репорт), рантайм-
патч для неё больше не нужен. Оставлено только правило для енота
(`Hips`/`UpLeg`), которое не вызывало подобных жалоб.

## Найдена настоящая причина "дыры" на шее — перебор при ручном выделении в Blender (пятьдесят пятый репорт)

Проверил гипотезу про "дыру в текстуре" — не подтвердилась (нет ни одной
вершины без привязки к костям вообще). Дело было в другом: сравнил,
какие именно вершины реально "уехали" из `Neck`/`LeftArm` при ручной
Blender-правке, против того, какими они были **до всякого редактирования**.

```
Neck:     убрано 407 — из них ЧИСТО на Neck (без примеси): 151
LeftArm:  убрано 748 — из них ЧИСТО на LeftArm (без примеси): 325
```

Это значит: при ручном выделении в Blender ("выделить хвост, снять
выделение с руки/шеи") часть **настоящей** анатомии шеи/руки случайно
попала в "снять и переназначить" вместе с хвостом. Переехав на `Spine2`
(кость с совсем другим поведением), эти вершины стали двигаться иначе,
чем соседние — растягивая треугольники сетки при анимации. Растянутый
треугольник сэмплирует текстуру по экстремальному градиенту UV — выглядит
как размытое/пустое пятно, легко спутать с "пропавшей текстурой".

**Хирургически точный фикс**: для каждой убранной вершины проверяю два
критерия — была ли она РЕАЛЬНО смешана с чем-то ещё в оригинале (значит
настоящая контаминация), ИЛИ геометрически чётко в зоне хвоста
(`X<-0.35, Z>0.35`, даже если формально "чистая" одной костью — это и
есть те самые "сиротские" вершины кончика хвоста без блендинга,
описанные ещё в тридцать четвёртом репорте). Если ни то, ни другое —
возвращаю как было в оригинале.

```
Neck:    двигаем 275 из 407 (возвращаем 132 настоящих)
LeftArm: двигаем 473 из 748 (возвращаем 275 настоящих)
```

**Проверка**: 0 вершин без веса, хвост 0 проблемных из 231, настоящая
анатомия вне зоны хвоста подтверждена побайтово идентичной оригиналу
(расхождение 716 вместо наивных 748 объясняется 32 вершинами,
контаминированными сразу и рукой, и шеей — посчитаны один раз, не дважды),
текстура и анимация не тронуты.

## Нашёл источник тусклости — увидел саму текстуру напрямую (пятьдесят третий репорт)

**Про размер**: механически проверил (не гипотеза) — сырые координаты
вершин в файле байт-в-байт идентичны до и после переноса PreRotation.
Наш расчёт масштаба использует именно эти данные через `Box3` в режиме
без учёта поз костей (стандартное поведение Three.js для skinned-мешей) —
PreRotation физически не мог повлиять на вычисленный масштаб. Жду цифры
из консольного лога (`[scene] FBX персонаж: исходный рост ... →
scale=...`), чтобы проверить по факту, а не продолжать гадать.

**Про цвет — нашёл, показав себе саму текстуру напрямую**, без всякого
Three.js-рендеринга. Извлёк JPEG из файла и посмотрел на неё: мех яркий
рыжий/оранжевый, глаза настоящие чёрные с белым. Значит, дело не в
картинке — она в порядке, проблема где-то в рендере.

Нашёл конкретного виновника: у материала `DiffuseColor = (0.8, 0.8, 0.8)`
— не чистый белый (1,1,1), а серый тон. Three.js перемножает
`material.color × texture.map` — если color не белый, вся текстура
тонируется в серый через умножение, теряя насыщенность и контраст
(включая зрачки — тоже темнеют к серому пропорционально). Раньше
`colorSpace`-фикс не помог визуально именно потому, что это была не та
причина — colorSpace отвечает за гамма-кодирование, а тут было буквальное
затемнение через умножение цветов.

Принудительно ставлю `material.color` в чистый белый при наличии текстуры
— раз есть полноценная цветная карта, она должна быть единственным
источником цвета, без дополнительного тонирования легаси Phong-свойством
из FBX.

## Три находки за раз: colorSpace, UnitScaleFactor, порядок операций (пятьдесят второй репорт)

По просьбе — искал корень, не гадал вслепую. Три отдельные, каждая
подтверждённая проверкой:

**1) Цвет/глаза — нашёл в НАШЕМ ЖЕ коде, не в данных файла.** Нигде в
`scene.js` не выставлялся `colorSpace` для загруженной текстуры и
`outputColorSpace` для рендерера — оба молча полагались на дефолты
библиотеки. Если diffuse-текстура (обычный JPEG) не помечена явно как
`THREE.SRGBColorSpace`, рендерер трактует уже гамма-кодированные цвета как
линейные — картинка выглядит смытой/тусклой, а тёмные пиксели (чёрные
зрачки) сдвигаются к серому. Это мог быть баг, который был в коде
ВСЕГДА — просто мы только сейчас впервые увидели реально работающую
текстуру, раньше она весь разговор была сломана (серый materal). Добавил
явную установку `colorSpace` на текстуре и `outputColorSpace` на
рендерере — не полагаемся на угадывание дефолтов конкретной версии Three.js.

**2) Размер — реальная разница в данных, но с оговоркой.** Сравнил
`GlobalSettings`: `UnitScaleFactor` — 100.0 в оригинале, 1.0 в файле после
Blender. Перенёс значение из оригинала. Честно: не до конца уверен, что
именно это объясняет "стала крупнее" — наш собственный код считает
масштаб автоматически по замеру реального роста после загрузки (не
полагаясь на абсолютные единицы), теоретически должен компенсировать
разницу сам. Но это подтверждённая реальная разница в данных, легитимный
фикс независимо от того, объясняет ли она весь эффект целиком.

**3) Порядок операций.** Удаление Light/Camera происходило ПОСЛЕ расчёта
габаритов для масштаба — переставил на самое начало обработки файла, до
всех остальных вычислений. Даже если это не влияло на итог (объекты без
геометрии обычно не расширяют bounding box в Three.js), порядок теперь
логически правильный.

**Проверка перед вшиванием**: текстура/хвост/анимация/отсутствие Light-Camera
подтверждены ещё раз, всё в порядке.

## Найден настоящий источник тусклости — встроенная лампа Blender с intensity=100000 (пятьдесят первый репорт)

Твоё замечание оказалось решающим: "свет и тени были даже на серой белке"
полностью опровергает мою гипотезу про текстуру (у плоского серого
материала нет собственных запечённых теней — взяться неоткуда). Значит,
дело было не в текстуре, а в чём-то на уровне сцены.

**Проверил прямо по твоей догадке** — сравнил количество `Light`/`Camera`
объектов в файлах:
```
ОРИГИНАЛ:            Light = 0, Camera = 0
FIXED3/ТЕКУЩИЙ:       Light = 1, Camera = 1
```

Подтвердилось: в диалоге экспорта были отмечены `Камера` и `Лампа` (это
видно на одном из твоих скриншотов настроек экспорта) — стандартные
объекты сцены Blender по умолчанию уехали прямо в FBX-файл вместе с
персонажем. Параметры лампы:
```
LightType: 0 (Point)
Intensity: 100000.0
CastShadows: 1
```

Intensity **100000** — Blender и FBX используют разные единицы измерения
яркости, отсюда такое огромное число. Если FBXLoader создавал из этого
настоящий `THREE.PointLight` и добавлял его в сцену — это объясняет разом
и передержанные ("тусклые" от избытка света) цвета, и странные тени от
источника, светящего совсем не оттуда, откуда наш собственный свет.

**Убрал Light и Camera объекты из файла** (оба Model-узла + их
NodeAttribute + все связи с ними) — проверил, что текстура (374КБ,
валидный JPEG), хвост (0 проблемных вершин) и анимация (вращение Hips
точно как в оригинале) остались нетронуты.

**Добавил защиту в код на будущее** — `loadCharacterFBX()` в `scene.js`
теперь после загрузки любого FBX-персонажа ищет и убирает любые встроенные
`THREE.Light`/`THREE.Camera`, кто бы их туда ни принёс. Если это повторится
с енотом или будущими персонажами — почини­тся автоматически, без ручной
бинарной хирургии каждый раз.

## Приглушил освещение сцены — эксперимент по гипотезе "двойных теней" (пятидесятый репорт, отменено)

Idle подтверждён рабочим после переноса PreRotation. Взялся за тусклость.

Проверил свойства материала между версиями раньше — они почти идентичны,
дело не в Blender-экспорте. Рабочая гипотеза: AI-генерированная текстура
уже содержит запечённое затенение (тени/AO от собственного рендера при

Это эксперимент, не гарантированное решение — не могу проверить

## "Лапы боком" — не хватало PreRotation при склейке (сорок девятый репорт)

Прошлая склейка перенесла кривые анимации (значения вращения), но не
учла, что вращение в FBX хранится ОТНОСИТЕЛЬНО "нулевой точки" каждой
кости (`PreRotation`) — а эта точка тоже часть данных файла, не
универсальная константа. Сравнил: у оригинала **каждая** кость имеет
`PreRotation` (например `mixamorig:LeftUpLeg`: `(5.98°, 0.07°, 179.33°)`),
у файла из Blender это поле **пустое у всех костей** — Blender использует
свою систему ориентации костей ("bone roll") и просто не сохранил их при
экспорте. Одни и те же числа вращения из анимации с разной "нулевой
точкой" дают разные позы — отсюда лапы, вывернутые в сторону.

Заодно нашёл вторую, скрытую часть той же проблемы: даже если
`PreRotation` присутствует, есть отдельный флаг `RotationActive` — без
него (`=1`) большинство FBX-парсеров ИГНОРИРУЮТ PreRotation целиком, даже
если он записан в файл. У оригинала этот флаг стоит у всех задействованных
костей, у файла из Blender — отсутствует полностью. Перенёс оба свойства
(`PreRotation`/`RotationOffset`/`RotationPivot`/`PostRotation`/
`ScalingOffset`/`ScalingPivot`/`RotationActive`/`RotationOrder`) из
оригинала в склейку, по каждой кости отдельно (23 кости).

**Проверка на этот раз — исчерпывающая, не выборочная:** сравнил ВСЕ 60
кривых вращения между оригиналом и склейкой (не 4-5 костей как в прошлый
раз) — 0 расхождений. Плюс текстура (374КБ, валидный JPEG) и хвост
(0 проблемных вершин из 231) подтверждены ещё раз.

## Покачивание — склеил файл вручную на бинарном уровне (сорок восьмой репорт)

**Диагностика:** сравнил кривые вращения кости `Hips` между оригиналом и
файлом после Blender. Оригинал — вращение в пределах пары градусов
(естественное лёгкое покачивание Idle). После Blender — X: 20°-184°,
Y: -96° до -90°, Z: -184° до -21° — вращение "улетело" в сотни градусов.
Выключение Apply Transform (третья попытка экспорта) **не помогло** —
цифры оказались абсолютно идентичны предыдущей версии. Значит, искажение
происходит на этапе ИМПОРТА в Blender (переинтерпретация ориентации
костей), не на экспорте — гонять больше попыток через Blender смысла
не было.

**Решение — написал полноценный читатель/писатель бинарного FBX** (не
только читать, как раньше, но и записывать обратно, сохраняя точный
исходный тип каждого поля — `S` vs `R`, `I` vs `L` и т.д., иначе рискуешь
незаметно испортить бинарные данные вроде встроенной текстуры).
**Проверил на безопасность round-trip тестом** — прочитал файл, записал
обратно без изменений, перечитал, сравнил дерево целиком: полная
идентичность.

**Склеил вручную**: скелет + меш + веса + текстура — из твоего
Blender-файла (там всё верно), а анимационные кривые (`AnimationStack`/
`AnimationCurveNode`/`AnimationCurve`) — из оригинала (где вращение было
правильным). ID костей между файлами не пересекались — пришлось
сопоставлять по ИМЕНАМ и переписывать 21 ссылку на кости в связях
(`Connections`), чтобы анимация из одного файла корректно указывала на
кости в другом.

**Проверил результат по всем фронтам, не только Hips:**
```

с оригиналом ПОЛНОСТЬЮ (не только диапазон, точные min/max)
```

## Серая белка — потерянная текстура при экспорте (сорок седьмой репорт)

**Причина:** в FBX текстура ссылается на `Video`-узел, а в нём — либо
встроенные байты картинки, либо просто путь к файлу. Ориginal-файл (из
Mixamo) хранил текстуру ВСТРОЕННОЙ — поэтому она и работала в браузере.
Мой совет по экспорту ("Path Mode не важен") был ошибкой — Blender по
умолчанию экспортировал только ССЫЛКУ на путь, а путь там был
серверный, от самого Mixamo (`C:\home\app\mixamo-mini\tmp\...`) —
никогда не существовавший на компьютере Stanislav. Отсюда серая белка —
Three.js не мог найти текстуру по такому пути и откатился на дефолтный
материал.

**Исправлено повторным экспортом** с `Режим пути: Копировать` +
включённой иконкой "Встроить текстуры" рядом с этим выпадающим списком (не
отдельная галочка ниже, как я сначала думал, а иконка справа от самого
списка). Проверил на бинарном уровне перед тем как вшивать:
- `Video` → `Content`: 374КБ встроенных данных (было 0)
- JPEG magic bytes (`\xff\xd8\xff`) корректны — валидный JPEG, не мусор
- Веса хвоста повторно перепроверены — 0 проблемных вершин, ничего не
  съехало при повторном экспорте
- AnimationStack на месте — Idle-анимация не потерялась

Файл `assets/character-fbx/Breathing_Idle.fbx` заменён на финальную
версию (с текстурой и починенным хвостом одновременно).

## "Современный аудиоплеер" — CSS-рестайлинг + свой waveform (сорок четвёртый репорт)

Отказались от идеи парсить sefon.pro (нелегально раздаёт музыку без прав —
не стал помогать с этим). Вместо этого — модернизация внешнего вида плеера,
по запросу показал оба возможных подхода сразу, чтобы можно было сравнить.

**Почему не Wavesurfer.js**: проверил на реальных GitHub issues библиотеки
— при аудио-backend'е она тоже вызывает `createMediaElementSource()` на
переданном `<audio>`-элементе и падает с ошибкой "HTMLMediaElement already
connected previously to a different MediaElementSourceNode". У нас этот
источник уже занят `audioAnalyzer.js` (ТЗ п.18 — можно создать только один
раз на элемент). Тянуть библиотеку ради этого не стал.

**Вариант A — CSS-рестайлинг** (применён везде, минимальный риск):
- Play-кнопка крупнее, с градиентом и мягкой тенью, hover/active-анимация
- Прогресс-бар — толще, с закруглением и градиентной заливкой "до текущей
  позиции" через CSS-переменную `--progress` (выставляется в `main.js`
  на каждый `timeupdate`/`input`) — классический приём для `<input
  type="range">`, раньше был просто плоский однотонный слайдер
- Панель плеера — лёгкий вертикальный градиент фона вместо плоского цвета
- Кнопки — везде `border-radius: 999px` (пилюли), единый стиль с уже
  существующими toggle-кнопками персонажей

**Вариант B — свой waveform, без библиотек** (`js/waveform.js`):
- Кнопка `〜` в панели плеера переключает обычный прогресс-бар на
  визуализацию волны трека
- `computeWaveformPeaks()` — декодирует выбранный файл в PCM ОДНОРАЗОВЫМ
  `AudioContext` (создаётся только для `decodeAudioData()`, сразу
  закрывается) — этот контекст никогда не подключается к `<audio>` и не
  участвует в реальном воспроизведении/анализе, поэтому конфликта с уже
  занятым `MediaElementSource` в принципе быть не может
- `drawWaveform()` рисует бары на `<canvas>` (позиционирован под
  прозрачным `#progress`, который остаётся функциональным для
  перетаскивания) — двухцветная заливка played/unplayed, обновляется на
  каждый `timeupdate`
- Декодирование идёт в фоне асинхронно, не блокирует воспроизведение —
  пока не готово, показывается плоская линия

## Клик по Duet закрывал меню вместо перехода в режим выбора (сорок третий репорт)

Баг с порядком всплытия события. Клик по кнопке Duet вызывает
`renderPicker()`, которая пересоздаёт содержимое пикера (`innerHTML=""` +
новые элементы) — включая саму кнопку, по которой только что кликнули —
прямо во время обработки ЭТОГО ЖЕ клика. Когда событие всплывает дальше до
`document`, наш обработчик "клик мимо — закрыть" проверяет
`avatarPickerEl.contains(e.target)` — а `e.target` это уже удалённый старый
узел кнопки, который физически больше не находится в дереве DOM. Проверка
ложно считает это "клик снаружи" и закрывает меню, не дав перейти в режим
выбора персонажей.

Исправлено — `avatarPickerEl.addEventListener("click", (e) =>
e.stopPropagation())`, повешено один раз на сам контейнер пикера (он не
пересоздаётся, в отличие от кнопок внутри него — меняется только его
`innerHTML`). Клики внутри пикера теперь вообще не доходят до
`document`-обработчика, независимо от того, что происходит с конкретными
кнопками при ре-рендере.

## Оба бага реальные — CSS-специфичность и Android-специфика (сорок второй репорт)

**"Меню не закрывается" — классическая ловушка CSS-специфичности.**
`#avatar-picker` имел явный `display: flex` в CSS. У ID-селектора
специфичность выше, чем у стандартного браузерного правила
`[hidden] { display: none }` (простой селектор по атрибуту) — поэтому
`avatarPickerEl.hidden = true` в JS честно проставлял атрибут, а
визуально ничего не менялось, наш же CSS её перебивал. Добавлено
`#avatar-picker[hidden] { display: none; }` — специфичнее обоих правил,
побеждает корректно.

**"Кружочек браузера остался" — прошлый фикс работал только в Safari.**
`-webkit-touch-callout` — свойство ТОЛЬКО для iOS/Safari, на Android оно
не действует вообще. На Android Chrome долгое нажатие на `<img>` ВСЕГДА
показывает системное меню картинки (открыть в новой вкладке, поиск через
Google Lens и т.д.) — и это принципиально не подавляется через CSS.

Настоящий фикс — не создавать `<img>` вообще. Аватарки теперь рисуются
как CSS `background-image` прямо на кнопке (`applyAvatarVisual()` в
`main.js`), а не дочерним `<img>`-элементом. У фонового изображения нет
собственного контекстного меню в принципе — браузеру физически нечего
показывать по долгому нажатию, вне зависимости от платформы.

## "Кружочек" браузера при долгом нажатии + доработка кнопки Duet (сорок первый репорт)

**"Кружочек" с иконкой глаза/точками** — это нативное меню мобильного
браузера при долгом нажатии на `<img>` (обычно "сохранить изображение" и
похожие пункты). Запрещено на уровне CSS (`-webkit-touch-callout: none`,
`-webkit-user-drag: none`, `user-select: none` на аватарках) и
подстраховано в JS (`contextmenu`/`dragstart` → `preventDefault()`) — на
случай, если конкретный браузер игнорирует CSS-свойство.

**Кнопка Duet теперь двухфазная**, как просили:
- В режиме "переключить" (`pickerMode === "switch"`) — обычная иконка 👯,
  всегда активна, клик переводит в режим выбора
- В режиме выбора — кнопка это уже ПОДТВЕРЖДЕНИЕ, не переключатель.
  Неактивна (`disabled`, приглушена), пока выбран только один персонаж.
  Как только выбрано двое — меняется на ✓, подсвечивается фиолетовым и
  становится кликабельной для подтверждения
- Подтверждение (`confirmSelection()`) всегда закрывает пикер и применяет
  выбор — раньше это тоже так работало, но неочевидность состояния кнопки
  создавала ощущение "не закрывается"

## "Avoid same dance" убрана совсем (сороковой репорт)

По итогам обсуждения — раз персонажи в Duet и так обычно танцуют разное
(независимые shuffle bag'и у каждого), функция решала не особо
существующую проблему, да ещё и без UI, где её включить. Убрано целиком:
`avoidSameDance`/весь блок в render loop (`main.js`), `avoidName`/
`setAvoidName`/условие в `danceBag` (`animationController.js`). Мешок
танцев снова фильтруется только по `disabledDances`, без учёта того, что
играет другой персонаж.

## Переработка UI выбора персонажа под будущее расширение (тридцать девятый репорт)

По просьбе — старая пара "ряд аватарок + отдельная кнопка Duet" заменена на
выпадающее меню, готовое под третьего (и далее) персонажа без переделки
логики.

**Новая модель состояния**: `activeCharacterIds` — массив id (порядок
важен, первый = "верхняя" панель), вместо прежних `duetMode`+`soloId`.
`computeOffsets(n)` расставляет N персонажей по X симметрично вокруг
центра — работает для 1, 2, 3+ персонажей одинаково, не только для двух
жёстко зашитых оффсетов.

**UI-поведение (как просили)**:
- Соло: одна аватарка + её синие кнопки. Клик по аватарке открывает
  попап ВВЕРХ с остальными персонажами (не активным сейчас) + иконкой 👯.
- Клик по персонажу в попапе → мгновенно переключает соло на него,
  попап закрывается.
- Клик по 👯 → переход в режим множественного выбора: попап показывает
  ВСЕХ персонажей как togglable-кнопки (клик добавляет/убирает из
  `pendingSelection`, попап не закрывается). Повторный клик по 👯 —
  подтверждает выбор.
- После подтверждения — вертикальный стек панелей `[аватарка][кнопки]`,
  по одной на каждого активного персонажа, панель над панелью.
- Если активных 2+, верхняя аватарка при клике сразу открывает попап в
  режиме выбора (не переключения) — можно быстро поменять состав.
- Клик мимо попапа — закрывает без применения (`document` click listener
  с проверкой `avatarPickerEl.contains`).
- Попап позиционируется `position: absolute; bottom: 100%` от
  `#dance-controls` — физически перекрывает сцену сверху панели, как и
  просили, не сжимается в рамках самой панели.

**Не переносил без уточнения**: кнопка "Avoid same dance" раньше жила
рядом с Duet-переключателем — в новой схеме для неё явного места в
описанном тобой флоу не нашлось. Переменная `avoidSameDance` и вся логика
мягкого избегания в `animationController.js`/render loop остались
рабочими (готовы к 2 персонажам), просто сейчас включить её негде в UI —
скажи, куда её поместить (например, маленькая иконка рядом с верхней
аватаркой, видимая только при 2+ активных), и подключу.

**Известное упрощение**: `computeOffsets`/камера для 3+ персонажей ещё не
проверялись визуально (сейчас есть только 2 реальных персонажа) — когда
появится третий, возможно, потребуется расширить кадр камеры отдельно.

## Откат: правки про наклон головы убраны (тридцать восьмой репорт)

Три попытки демпфирования (только Head → Spine+Head → вся цепочка
Spine/Spine1/Spine2/Neck/Head) не дали устраивающего результата — по
запросу откачено полностью. `loadAnimationClipsFBX()` в `scene.js`
вернулась к исходному простому виду: загружает клип, переименовывает по
`clipName`, ничего больше не трогает. Функция `dampenBoneRotation` и все
её вызовы удалены.

Технически подход был обоснованным (нашли реального виновника — Spine
поворачивается на ~60°, больше чем сама голова) и код работал именно так,
как задумано (подтверждено логами), но результат на глаз всё равно не
устроил — видимо, наклон настолько глубоко часть самой хореографии
хип-хопа, что убрать его без искажения остального движения затруднительно
через простое демпфирование к нейтральной позе.

## Все ещё наклонена голова — гасили не всю цепочку (тридцать седьмой репорт)

Прошлый фикс трогал только `Spine` и `Head`, оставляя `Spine1`, `Spine2` и
`Neck` полностью нетронутыми. По отдельности каждая из них небольшая
(~10-17°), но втроём всё ещё ощутимо наклоняли голову вперёд — именно это
и было заметно.

Расширил на всю цепочку разом: `Spine` (0.5, самый большой вклад ~60°),
`Spine1`/`Spine2` (0.6 каждая), `Neck` (0.5), `Head` (0.4, как раньше).
Проверил через `endsWith` на реальных именах костей — каждый hint
матчит ровно свою кость, никаких пересечений между Spine/Spine1/Spine2.

Если наклон всё ещё будет заметен — можно либо сильнее ужать конкретные
кости (цифры в вызовах `dampenBoneRotation()` внутри
`loadAnimationClipsFBX()`), либо признать, что это уже часть самой
хореографии хип-хопа настолько, что убрать её без искажения остального
танца сложно — тогда, возможно, разумнее просто выбрать другой танец
из пула для этого стиля движения, чем продолжать давить конкретные кости.

## Демпфер головы не помог — настоящий виновник Spine, не Head (тридцать шестой репорт)

Проверил по скриншоту консоли — код реально срабатывал (`dampenBoneRotation:
приглушено вращение "mixamorigHead"`), просто гасил не ту кость. Разобрал
реальные амплитуды вращения по осям в хип-хоп клипе:

```
mixamorig:Spine   Z: диапазон 59.9°  ← основной виновник
mixamorig:Head    Z: диапазон 45.0°
mixamorig:Neck    Z: диапазон 16.6°
```

`Spine` (у самого основания позвоночника, ближе к бёдрам) поворачивается
почти на 60° по Z — больше, чем сама голова. Корпус наклоняется вперёд в
танце, и голова "падает" вместе со всем телом через цепочку
`Spine → Spine1 → Spine2 → Neck → Head`, а не потому что голова сама
активно кивает. Демпфирование только `Head` гасило лишь добавку сверху, а
не основной наклон — отсюда "не помогло".

Заодно нашёл и починил сопутствующий баг в самом матчинге: поиск кости
через `track.name.includes("Spine")` случайно поймал бы и `Spine1`,
и `Spine2` (это разные кости, includes видит подстроку). Заменил на
`endsWith` — теперь `"mixamorigSpine1".endsWith("Spine")` корректно даёт
`false`, а `"mixamorigSpine".endsWith("Spine")` — `true`.

Теперь демпфируются обе кости: `Spine` умеренно (`dampingFactor=0.6` —
уменьшает общий наклон корпуса, но не сплющивает танец совсем) и `Head`
как раньше (`dampingFactor=0.4` — добавочная стабилизация самой головы
поверх уже менее наклонённого корпуса).

## Голова/подбородок не заваливается вниз на хип-хоп клипах (тридцать пятый репорт)

Проверил на реальном файле — кость `mixamorig:Head` действительно
анимирована (`Lcl Rotation`) в хип-хоп клипах у обоих персонажей, есть что
приглушать.

**В отличие от истории с хвостом, здесь НЕ пришлось парсить сырые кривые
из бинарного FBX и гадать с осями/конвенциями.** FBXLoader сам собирает
покадровые данные в готовые `THREE.QuaternionKeyframeTrack` — работаем с
ними напрямую после загрузки, никакого риска ошибиться с координатной
системой конкретного файла.

`dampenBoneRotation()` в `scene.js`: для каждого кадра клипа слерпит
кватернион кости `Head` от нейтральной bind-позы персонажа (голова стоит
ровно) к оригинальному значению анимации, на `dampingFactor` (по умолчанию
0.4 — заметно приглушено, но не заморожено полностью). Подключено только
для клипов, чьё имя начинается с `"hiphop"` (`hiphop_1`...`hiphop_7`) — по
запросу, остальные танцы не трогаются.

**Честно про компромисс:** глушится вращение головы целиком, не только
"вниз" — не было возможности узнать без визуальной проверки, какая именно
локальная ось у этого рига отвечает конкретно за "смотреть вниз", поэтому
взял более безопасный путь — приглушить любое отклонение от нейтрали
сразу. Значит, лёгкие естественные повороты головы в стороны в танце тоже
станут скромнее, не только наклон вниз.

**Проверь и подстрой при необходимости**: если голова стала слишком
"замороженной" — `dampingFactor` можно поднять (ближе к 1 = меньше
приглушения); если подбородок всё ещё заметно уходит вниз — опустить
(ближе к 0). Значение зашито в вызове `dampenBoneRotation()` внутри
`loadAnimationClipsFBX()` — единственное место, которое нужно поменять
для обоих персонажей сразу.

## Плечи стали острее — откатил лишнее правило (тридцать четвёртый репорт)

Правило "LeftShoulder/RightShoulder как якорь для LeftArm" зацепило не
только оставшиеся вершины хвоста, но и НАСТОЯЩИЕ вершины сустава
плечо-рука — убрало их нормальное сглаживание с рукой, отсюда острые,
более жёсткие плечи. Цена оказалась больше пользы (спасало только часть
кончика хвоста, ~78 из 231 вершины, а плечи портило заметно) — убрал
правило целиком, вернулись к трём рабочим (Hips/UpLeg + Spine2 с двумя
вариантами).

**Про "просто отрезать" оставшуюся плавающую вершину хвоста** — идея
разумная, но не как ещё одно правило по именам костей: та же проблема,
что только что испортила плечи, повторится — кости `LeftArm`/`Neck`
целиком держат и настоящие вершины руки/шеи, и "сиротские" вершины
кончика хвоста, по весам они неотличимы. Разделить их можно только по
ГЕОМЕТРИЧЕСКОЙ позиции конкретной вершины — а для надёжного порога там
нужна визуальная проверка, которой у меня в песочнице нет (уже один раз
ошибся вслепую с плечами).

Для этого конкретного случая (мелкая полировка кончика хвоста, ~78 вершин
из 6000+) правильный инструмент — Blender: там можно кликом выделить
именно эти вершины в режиме Weight Paint или Edit Mode и либо
перепривязать их вручную, либо действительно удалить — с мгновенной
визуальной обратной связью, а не гаданием по сырым числам. Займёт
буквально пару минут, раз Blender уже есть и опыт работы с ним тоже.

## Хвост белки — другая проблема, другие кости (тридцать третий репорт)

У еноты фикс сработал, у белки — нет, потому что там **другая** проблема.
Хвост белки в T-позе загнут вверх через спину к плечу (у енота — лежит
у основания спины), поэтому и контаминация там между другими костями:
`Spine2`, `LeftArm`, `LeftShoulder`, `Neck` — заметно более подвижные
кости в танце (руки активно машут), чем нога у енота, отсюда и более
сильное "плавание".

Расширил `rigidifyContaminatedSkinWeights()` — теперь принимает НАБОР
правил вместо одного, каждое применяется независимо и безвредно для
персонажей без такого сочетания костей. Добавил правила под находку у
белки: якорь `Spine2` для вершин, смешанных с рукой/плечом/шеей, и
отдельно якорь `LeftShoulder`/`RightShoulder` для вершин, смешанных ТОЛЬКО
с рукой без Spine2 вообще (плечо двигается заметно меньше самой руки при
взмахах — не идеальный, но кратно более стабильный якорь).

**Проверил на реальных данных** (не на глаз): из 231 проблемной вершины
хвоста белки новые правила закрывают 153 (66%). Остаются 78 вершин — это
УЖЕ не смешение (contamination) в прежнем смысле: они **полностью, на
100%**, висят одной костью на `LeftArm` или `Neck`, без единой капли
`Spine2`/`Shoulder`. Это другой тип проблемы — не растяжение между двумя
конкурирующими костями, а целый кусок кончика хвоста жёстко едет вместе с
рукой/шеей отдельно от остального хвоста. Починить по именам костей
нельзя (у этих вершин просто нет второй кости, за которую можно
зацепиться) — там нужна привязка по геометрической позиции вершины, а не
по весам, что требует более сложного (и менее надёжного без визуальной
проверки) подхода. Отложил до проверки, станет ли лучше уже с этим фиксом.

## У енота всё стало хорошо. У белки ещё плавает хвост в некоторых местах

## Фикс хвоста почти не подействовал — нашли, каких вершин не хватало (тридцать второй репорт)

Проверил гипотезу про "скин в каждом файле танца" — архитектурно это не
может быть причиной: `loadAnimationClipsFBX()` никогда не подключает меш
из танцевальных файлов, только сами кривые анимации. Скин всегда только
из `Breathing_Idle.fbx`. Значит, проблема была в самом фиксе.

Прогнал полный анализ всех 200 вершин хвоста (не выборку, как в прошлый
раз) — оказалось, 111 из них смешаны между `Hips` и `LeftUpLeg`, и у **48
из них именно нога перевешивает** по весу, не бёдра. Первая версия фикса
требовала, чтобы `Hips` уже был доминирующим (>50%) — эти 48 вершин просто
не попадали под условие и оставались фактически "на ноге", что и давало
самое заметное растяжение при активном движении ног в танце.

Убрал требование "уже доминирует" — теперь любая вершина с одновременным
весом и на `Hips`, и на `UpLeg`-кости жёстко разрешается в пользу `Hips`,
независимо от того, что там сейчас перевешивает. Теперь под фикс попадают
все 111 смешанных вершин, а не только 63 из них.

Возможный побочный эффект: это может слегка задеть и настоящие вершины
стыка нога-бедро (там небольшое смешение — нормальная практика для
гладкого сгиба сустава при ходьбе), но у Mixamo-риггинга такое смешение
обычно узкий "ободок" вершин, а не 200+ вершин целого хвоста — если
появится заметный залом на самом бедре, скажи, сузим условие обратно.

## Хвосты "текут" на некоторых движениях — нашли и починили на уровне весов скина (тридцать первый репорт)

Разобрал бинарный FBX енота вручную (Deformer/Cluster/Connections —
таблица связей "кость → какие вершины меша и с каким весом"), чтобы не
гадать. Нашёл точную причину:

**У Mixamo-риггинга нет отдельной кости для хвоста** — веса вершин хвоста
автоматически размазались по ближайшим костям скелета при авто-риггинге.
Большая часть хвоста жёстко (100%) держится на `Hips` — это нормально. Но у
САМОГО ОСНОВАНИЯ хвоста нашлись вершины, размазанные между `Hips` и
`LeftUpLeg` (нога) — потому что геометрически они рядом в T-позе:

```
vert 6145: LeftUpLeg=0.73, Hips=0.27
vert 6115: LeftUpLeg=0.86, Hips=0.14
```

Когда нога активно двигается (шаги, приседания в танце), эти немногие
"смешанные" вершины утягиваются вслед за ногой, пока остальной хвост
остаётся с бёдрами — визуально это и читалось как "хвост растягивается".

**Фикс — `rigidifyContaminatedSkinWeights()` в `scene.js`**, вызывается
один раз сразу после загрузки персонажа. Находит по ИМЕНИ кости, где
"Hips" уже доминирует (>50% веса), но есть примесь от кости с "UpLeg" в
названии — и жёстко перепривязывает такую вершину на 100% к Hips, обнуляя
чужой вес. Работает по именам костей, не по геометрии — не привязано к
конкретному персонажу или ориентации осей конкретного FBX-файла, должно
сработать и для белки, если у неё похожая проблема (просто ничего не
изменит, если проблемы нет — `fixedCount` будет 0).

## Откат: убрали пол и всю систему коррекции (тридцатый репорт)

После нескольких итераций (жёсткий клэмп → динамическая коррекция через
precise Box3 → попытка отделить от приседа) так и не удалось до конца
избежать либо проваливания, либо парения персонажа на каких-то конкретных
клипах — по указанию Stanislav решили не гнаться за этим дальше.

**Что сделано:**
- Пол убран из сцены целиком (`createScene` в `scene.js`) — без видимой
  опорной поверхности расхождение в несколько мм/см между клипами просто
  не видно на экране
- `groundAndCenterModel()` вернулась к простой версии: ставит персонажа по
  нижней точке bind-позы Idle-клипа один раз при загрузке, без запаса и
  без коррекции
- Вся система динамической коррекции пола (`groundProbeBox`,
  `groundCorrectionTimer`, `targetGroundLift`, `smoothedGroundLift`, все
  связанные параметры tuning) удалена из `animationController.js` — вместе
  с процедурными реакциями (присед, покачивание) это закрывает всю
  историю багов с полом за последние ~10 репортов

`model.position.y`/`model.rotation.y` теперь вообще не трогаются
процедурно в `reactToAudio()` — персонаж стоит там, где его один раз
поставил `groundAndCenterModel()` при загрузке, и это всё, что определяет
его положение в пространстве. Вся "реакция на музыку" теперь — это только
выбор/переключение готовых танцевальных клипов и скорость их
воспроизведения.

## Покачивание корпусом тоже убрано — та же категория, что и присед (двадцать девятый репорт)

Важное уточнение от Stanislav на будущее: исходный ТЗ (самое первое
техзадание в начале проекта) писался под персонажа с чисто утилитарными
Quaternius-анимациями (`Idle_Loop`/`Dance_Loop`), где в самом движении не
было ничего "музыкального" — процедурные реакции (присед п.7, акцент-прыжок
на бит) были ЕДИНСТВЕННЫМ способом дать видимую связь с музыкой. Именно
поэтому в Phase 9 они и появились.

С переходом на настоящие Mixamo mocap-клипы эта работа уже сделана
профессиональным аниматором внутри самого клипа — вес, баланс, акценты.
Накладывать сверху ещё и синтетику избыточно и буквально конфликтует с уже
заложенным в данные движением (это и была причина всей серии багов с полом
в последних репортах). Роль контроллера сместилась с "имитировать танец
процедурно" на "правильно выбирать и переключать готовые танцы в такт
настроению музыки" — tier-логика, shuffle bag, timeScale под темп, плавные
переходы на границах цикла.

Убрано и покачивание корпусом (`swayAmount`/`swaySpeed`) — та же категория,
что и присед, просто не успело вызвать явных багов (это было вращение, не
позиция, поэтому не спорило с полом). `model.rotation.y` больше не
трогается процедурно — вращение персонажа теперь целиком определяется
играющим клипом.

**На будущее:** для новых персонажей с Mixamo/mocap-анимациями процедурные
реакции поверх скелета в этом духе, скорее всего, не нужны в принципе —
разве что для чего-то, чего в принципе нет ни в одном клипе (например,
специфичный эффект типа свечения/частиц, а не движение тела).

## Присед от баса убран совсем (двадцать восьмой репорт)

По итогам обсуждения — присед был реализацией ТЗ п.7 ("чем сильнее bass,
тем сильнее персонаж приседает"), но по факту стал источником почти всех
багов с проваливанием/улётом персонажа за последние несколько репортов.
Визуальная польза была скромной (5см на фоне полноценных танцевальных
движений), а сложности — непропорционально большими. Убрали совсем.

Заодно упростилась и сама коррекция пола — раньше нужен был трюк с
временным откатом `position.y` к `baseY` перед замером именно чтобы
отделить "проваливание клипа" от "нашего же приседа". Без приседа
мешать замеру больше нечему — `position.y` на момент замера и так уже
чистый `baseY`, можно мерить напрямую.

Осталась только процедурная реакция на покачивание корпусом от intensity
(поворот, не влияет на высоту) — и динамическая коррекция пола, которая
теперь решает ровно одну задачу: компенсировать разницу в скелетной позе
между разными танцевальными клипами, ничего больше не путая.

## Белка слегка приподнята — коррекция путала присед с проваливанием клипа (двадцать седьмой репорт)

Попросили не торопиться — разобрался как следует, прежде чем править.

**Причина:** замер (`groundProbeBox.setFromObject`) происходил ПОСЛЕ того,
как в `position.y` уже подмешан присед от баса
(`model.position.y = baseY - smoothedVisualBass * squatAmount`, строка
чуть выше). Если в момент периодического замера (раз в 0.15с) играл хоть
небольшой бас — присед уже сдвинул модель вниз на несколько сантиметров, и
коррекция принимала этот НАШ ЖЕ, намеренный присед (ТЗ п.7 — реакция на
музыку) за проваливание клипа и начинала его компенсировать, вздёргивая
персонажа выше нужного. У енота эта ошибка ЧАСТИЧНО совпадала по
направлению с реальной проблемой (тоже "поднять") и маскировала себя, у
белки реальной проблемы не было — и лишняя компенсация была видна как
чистое "приподнят над сценой".

**Исправлено** — на время замера временно откатываем `position.y` к
чистому `baseY` (без приседа), меряем реальное положение ИМЕННО клипа
относительно этой базовой точки, возвращаем присед обратно. На экране
переключение не видно — рендер кадра происходит позже, за пределами этого
блока кода, синхронного с ним. Теперь коррекция реагирует только на
настоящую разницу между клипами, не путает её с собственной музыкальной
реакцией.

## Персонажи улетали вверх за экран — баг в самой коррекции (двадцать шестой репорт)

Реальная ошибка в математике, не про нагрузку. В момент замера
(`groundProbeBox.setFromObject`) `position.y` ещё НЕ содержит коррекцию с
текущего кадра — она применяется на строку ниже
(`model.position.y += smoothedGroundLift`), уже после замера. Код ошибочно
вычитал `smoothedGroundLift` из свежего замера, как будто тот уже её
учитывает — это искусственно завышало цель на каждом цикле пересчёта
(каждые 0.15с), без какого-либо ограничения сверху. Результат — коррекция
copilась бесконечно, и персонажи улетали вверх за пределы экрана во время
танца (не сразу — только когда циклов пересчёта накопилось достаточно).

Исправлено — убрано ошибочное вычитание. Заодно добавлен защитный потолок
`maxGroundLift = 15см` на саму коррекцию — на случай похожих багов в
будущем, коррекция физически не сможет разогнаться в бесконечность, чем бы
она ни была вызвана.

## Настоящая причина: скелетная деформация внутри клипа, не позиция объекта (двадцать пятый репорт)

Прошлый клэмп не сработал, потому что двигал только `model.position.y` —
позицию персонажа КАК ЦЕЛОГО объекта. Но "проваливание" именно на
Hip Hop 1 у енота (и не у белки) — это, судя по всему, движение
бёдер/корпуса ВНУТРИ самой анимации (baked keyframes на кости Hips),
из-за более коротких пропорций ног у енота относительно того, на чём
изначально снимался mocap — глубина приседа в самом движении оказывается
больше относительно роста персонажа. Такое клэмп на уровне объекта
принципиально не видит — это скелетная деформация (skinning), а не
трансформ объекта.

**Исправлено честно, не приблизительно.** Периодически (раз в 0.15с, не
каждый кадр — дорого) меряем РЕАЛЬНЫЙ нижний край персонажа через
`Box3.setFromObject(model, true)` — второй параметр `precise=true`
заставляет Three.js учитывать текущую скелетную позу (реальные
skinned-вершины), а не bind-позу, как было раньше везде. Если нижняя точка
уходит ниже пола — вычисляем, насколько нужно поднять, и плавно (не
скачком) подмешиваем эту коррекцию к позиции каждый кадр. Работает для
ЛЮБОГО клипа с ЛЮБОЙ глубиной движения, не требует ручного подбора
запаса под конкретный танец.

## Все равно проваливается — прошлый клэмп не сработал (двадцать четвёртый репорт, продолжение)

## Асимметрия в Duet — белка не переставлялась при включении режима (двадцать третий репорт)

**Причина:** `applyMode()` грузил только "недостающих" персонажей
(`desired.filter((id) => !slots[id])`) — если белка уже была загружена в
соло (по центру, `offsetX=0`) до включения Duet, код не считал её
"недостающей" и просто оставлял на месте. Переставлялся только реально
догружаемый енот (в `-0.9`), белка оставалась в `0` — отсюда видимая
асимметрия, енот у края, белка как будто всё ещё в одиночном центре.

Исправлено — каждый слот теперь помнит свой `offsetX`. При смене режима
для персонажей, которые уже были загружены, но требуют другой позиции,
`applyMode()` сдвигает модель на разницу между старым и новым offsetX,
а не полагается только на факт "загружен/не загружен".

## Проваливание в пол на танцевальных клипах (двадцать второй репорт)

**Причина:** высота "на полу" ставится один раз, по клипу Breathing Idle.
Но разные Mixamo-клипы — это разные mocap-записи, и высота корневой кости
(Hips) в состоянии покоя у них может отличаться на несколько мм между
клипами. У енота это оказалось заметно — на танцевальных клипах он
проваливался в пол примерно на полсантиметра относительно того, где
"нулевую" высоту зафиксировал Idle.

Не стал чинить это динамическим пересчётом на лету при каждой смене клипа
— слишком велик риск снова словить "телепорт", с которым уже разбирались
раньше (баг седьмого репорта). Вместо этого — `FLOOR_SAFETY_MARGIN = 8мм`:
персонаж ставится с небольшим запасом высоты, так что мелкий уход "в
минус" у любого клипа (в пределах ~8мм) больше не проваливает его сквозь
пол. Если какой-то клип, наоборот, окажется чуть выше нормы — будет едва
заметно парить, что визуально куда менее заметно и неприятно, чем
проваливание в текстуру.

## Позиции местами + камера не отдаляется в Duet (двадцать первый репорт)

- Енот теперь слева (`offsetX: -0.9`), белка справа (`offsetX: 0.9`) —
  раньше было наоборот
- Камера в Duet больше не отъезжает — та же позиция `(0, 1.4, 5.0)`, что
  и в соло. Если персонажи будут казаться тесно стоящими или слегка
  обрезанными по краям кадра — это ожидаемо, отдаление убрано по просьбе

## Duet-режим: оба персонажа одновременно (двадцатый репорт)

**Да, реализовано.** Потребовалась серьёзная переработка — раньше вся
архитектура (`mixer`, `animController`, `characterModel`) была рассчитана
на ровно одного активного персонажа. Теперь это система "слотов":

```js
const slots = {}; // id -> { model, mixer, animController, disabledDances, lastNowPlayingName }
```

- **Соло** (по умолчанию): один слот, персонаж по центру
- **Duet** (кнопка "👯 Duet"): оба слота сразу — белка слева (x=-0.9),
  енот справа (x=+0.9), `groundAndCenterModel()` получил параметр
  `offsetX` специально под это. Камера отъезжает чуть дальше, чтобы оба
  влезли в кадр
- `applyMode()` — центральная функция, приводит набор загруженных слотов к
  желаемому (выгружает лишнее через `disposeObject3D`, догружает
  недостающее), вызывается и при клике на аватарку (клик всегда переводит
  в соло с этим персонажем), и при клике на Duet

**"Не танцевать одинаковое одновременно" — сделано мягким, не жёстким
запретом**, как и просил. В `animationController.js` — `setAvoidName(name)`:
danceBag, выбирая следующий танец, пытается исключить имя, которое сейчас
играет партнёр, но **только если после исключения в пуле останется хотя бы
один вариант**. Если включён один-единственный танец у обоих (или так
совпало, что именно этот — следующий по очереди в мешке) — совпадение всё
равно произойдёт, это ожидаемо. Управляется кнопкой "🚫 Avoid same"
(появляется только в Duet-режиме), которая каждый кадр сообщает обоим
контроллерам `getCurrent()` друг друга.

**Панель кнопок** в Duet показывает оба пула с мини-заголовками ("Squirrel"
/ "Raccoon"), потому что имена клипов могут совпадать между персонажами
(`hiphop_1` есть у обоих) — кнопки различаются составным ключом
`characterId::clipName`, а не только именем клипа.

**Известное ограничение**: если открыто с `?debug=1`, `OrbitControls`
может переопределить программную позицию камеры на следующем кадре — в
debug-режиме камера всё равно управляется мышкой, это не баг, а
взаимодействие двух источников управления камерой.

## Мультиперсонажность: добавлен енот (девятнадцатый репорт)

## UI-доработки: баг с canvas, подсветка текущего танца, убрана кнопка Beat, аватарка (шестнадцатый репорт)

**Баг "кнопки прячутся, зум чинит".** Причина — `renderer.setSize()` в
three.js сам проставляет canvas инлайновые `style.width`/`style.height` в
пикселях (не CSS-проценты). Мы вызывали его один раз при создании сцены —
в этот момент `#dance-controls` был ещё пустым `<div>` (кнопки строит JS
чуть позже), поэтому canvas получал размер, посчитанный БЕЗ учёта будущей
панели, и оставался зафиксирован на нём. Зум колёсиком триггерит `window
resize`, на который мы уже подписаны — оттуда и лечило временно. Исправлено:
явно вызываем `resize()` (теперь экспортируется из `createScene`) сразу
после построения кнопок и после загрузки аватарки.

**Фиолетовая подсветка "танцует сейчас".** У кнопки теперь два визуальных
состояния одновременно: `aria-pressed="true"` (синяя — включено в ротацию)
и класс `.now-playing` (фиолетовая — реально играет в данный момент).
Обновляется в render loop через `animController.getCurrent()`, только при
смене (не каждый кадр). Явно очищается на паузе — иначе подсветка
оставалась бы висеть на последнем танце.

**Кнопка Beat убрана целиком** вместе с механизмом позиционного "хлопа"
(`beatPopEnvelope`/`beatPopHeight`/`beatPopAttackTau`/`beatPopDecayTau` — всё
удалено из `animationController.js`). `reactToAudio()` больше не принимает
`beat`. `beatDetector` продолжает работать для debug-панели (`?debug=1`) —
не выключил само определение битов, просто убрал его влияние на анимацию.

**Аватарка персонажа** — `assets/ui/squirrel-avatar.png` (уменьшено с 2.4МБ
до 6КБ через sharp, 128×128), слева от панели кнопок. `#dance-controls`
теперь `<img id="character-avatar">` + `<div id="dance-buttons">` — задел
на будущее под несколько персонажей: когда их станет больше, у каждого
будет своя аватарка + свой набор кнопок стилей танцев в этой же панели.

## Idle реже срабатывает (пятнадцатый репорт)

Подтверждено — исчезновение дребезгов совпало с переносом shuffle в общий
пул, был прав. Дальше: idle всё ещё иногда включался во время в целом
энергичного трека — снизил чувствительность:

- `INTENSITY_ACTIVE_DOWN`: 0.25 → **0.12** — чтобы уйти в calm, нужен
  по-настоящему тихий момент (близко к самому тихому месту трека), а не
  обычный локальный спад громкости внутри энергичной части
- `calmConfirmSeconds`: 0.4 → **0.8** — новое состояние должно продержаться
  почти секунду, а не 0.4с, прежде чем персонаж на него отреагирует

Порог входа в active (`INTENSITY_ACTIVE_UP = 0.35`) не трогал — жалобы на
слишком редкое появление танца не было.

## Убрали "light"/shuffle как отдельное состояние (четырнадцатый репорт)

По просьбе — упростили модель состояний с трёх до ДВУХ: `calm` (idle) и
`active` (пул танцев). Раньше `shuffle` был отдельным промежуточным
tier'ом между idle и полноценным танцем со своим порогом гистерезиса и
debounce — источник части сложности и потенциальных мест для дребезга.

Теперь:
- `DANCE_POOL` — **12** танцев (11 прежних + `shuffle`, который стал рядовым
  участником пула наравне с остальными, просто более спокойным по стилю)
- Один порог с гистерезисом вместо двух: вход в "active" при intensity >
  0.35, выход обратно в "calm" при intensity < 0.25
- `activeConfirmSeconds`/`calmConfirmSeconds` — debounce остался, защищает
  ровно те же два перехода, что и раньше, просто теперь это единственная
  граница вместо двух
- Панель кнопок — теперь 12 переключателей, `Shuffle` кнопка добавлена

## Объединение пула + панель live-контроля (тринадцатый репорт)

**Слил акценты в общий пул.** Раньше 4 клипа (`uprock_brooklyn`,
`uprock_breakdance`, `twerk`, `maraschino`) были отдельным `ACCENT_POOL` —
включались мгновенно (0.1с fade) поверх основного танца на сильный beat, в
обход обычного "ждём конца лупа" механизма. Это было живым подозреваемым в
остаточном дребезге при переходах. Теперь все 11 танцев — **один** пул
(`DANCE_POOL`, экспортируется из `animationController.js`), ротируются
через тот же shuffle bag, что и раньше, с тем же уважением к концу текущего
цикла. `strongBeat` больше не используется в `reactToAudio` — весь
механизм отдельного "акцента" убран, что заодно должно сгладить часть
оставшихся мелких дребезгов при переходе между танцами.

**Новая панель между сценой и плеером** — 11 кнопок, по одной на танец
(`Hip-Hop 1-5`, `Samba`, `Silly`, `Uprock BK`, `Uprock BD`, `Twerk`,
`Maraschino`). Все включены по умолчанию. Клик выключает танец из живой
ротации — `animController.setDanceEnabled(name, false)`:
- Если выключаемый танец не играет прямо сейчас — просто пропадает из
  будущих розыгрышей shuffle bag
- Если играет прямо сейчас — не обрывается резко, ставится "в очередь" на
  замену тем же механизмом, что и обычная ротация (ждёт конца лупа)
- Если пользователь выключит все 11 — персонаж не ломается, откатывается
  на `shuffle`, пока хотя бы один танец не включат обратно

Кнопки строятся в `main.js` из экспортированного `DANCE_POOL` — единый
источник правды с `animationController.js`, список имён не дублируется.

## Проверка

Погоняй трек, повыключай несколько кнопок на лету — персонаж должен
переставать выбирать выключенные танцы (кроме, может быть, самого текущего
до конца его цикла), но не спотыкаться при этом. Включи обратно — должны

дребезгов" на переходах танец-танец теперь, когда акценты не врезаются
отдельным быстрым fade.

## Дребезг по ВРЕМЕНИ, не по амплитуде (одиннадцатый-двенадцатый репорт)

**Баг: "визуально начинает shuffle, через долю секунды дёрганье в танец".**
Гистерезис по амплитуде (два порога вместо одного) защищает от шума
СИГНАЛА, но не защищает от быстрого перепада: если музыка резко перескакивает
тихо→громко буквально за доли секунды, "light" всё равно формально
пересекается — просто очень быстро. Персонаж успевал среагировать на
shuffle, а через мгновение уже на "active" — визуально читалось как
дёрганье между двумя состояниями.

Первая версия фикса добавляла debounce **на все** переходы состояний — но
это оказалось слишком грубо: "shuffle почти перестал появляться, зато idle
слишком часто". Причина — light/calm по природе часто бывают короткими
переходными состояниями между тихим и громким, а общий debounce их
"проглатывал", перескакивая сразу между calm и active мимо shuffle.

**Исправлено — debounce стал избирательным**, защищает ДВА конкретных
перехода, а не все подряд:
- Вход в **active** (из calm ИЛИ light) — требует `activeConfirmSeconds`
  (0.18с). Это чинит исходный баг: быстрый проскок через "light" не должен
  успевать включить shuffle перед мгновенным переключением в танец.
- Вход в **calm** — отдельно, требует `calmConfirmSeconds` (0.4с, дольше,
  чем active). Без этого короткая пауза/затишье внутри в целом энергичного
  трека (тихий такт, скретч, дыхание перед припевом) мгновенно ронял
  персонажа в Idle прямо посреди танца — визуально выглядело так, будто
  белка "сдаётся" на ровном месте.
- **Вход в light** — по-прежнему БЕЗ задержки, применяется сразу. Это
  переходное состояние по природе короткое, и если его тоже придушить
  debounce'ом (как было в самой первой версии фикса), shuffle почти
  перестаёт появляться вообще.

## Проверка

Shuffle должен появляться нормально между idle и полноценными танцами. Вход
в танец — без вспышки shuffle перед ним. А во время в целом энергичного
отрезка трека короткие паузы/затишья больше не должны ронять персонажа в
Idle — только по-настоящему устойчивое затихание музыки.

## Адаptivная intensity — вместо констант, подобранных под один трек (десятый репорт)

**Баг: "на некоторых треках только shuffle+idle, другие танцы редко".**
Причина глубже, чем пороги гистерезиса — сама формула intensity
(`volume*2.6*0.35 + bass*0.65`) была откалибрована на одном тестовом треке
(Coolio). У других треков средняя громкость/бас другие — даже в самых
энергичных местах трек мог физически не дотягивать до порога "active"
(0.55). Это не про дребезг на границе (тот уже починен гистерезисом), а
про то, что сам сигнал для многих треков просто не забирался высоко
настолько, насколько предполагала формула.

Исправлено — `createIntensityTracker` теперь работает как автоматическая
регулировка усиления (AGC), знакомая по аудиотехнике: вместо сравнения с
зашитыми числами, каждую секунду отслеживаются "огибающие" — насколько
громко/тихо было **в этом самом треке** за последние ~несколько секунд.
Intensity вычисляется относительно этого диапазона: самое тихое место
трека всегда около 0, самое громкое место ЭТОГО трека — всегда около 1,
независимо от абсолютного мастеринга записи. Огибающие быстро тянутся к
новым пикам/затишьям (2.5с) и медленно отпускают старые (20с) — не
дёргаются от единичного громкого удара, но и не залипают на старом уровне
надолго.

## Проверка

Проверь именно те треки, где раньше был почти только shuffle+idle — теперь
"активная" часть (полный пул из 7 танцев) должна включаться в их
собственных громких местах, даже если в абсолютных цифрах трек тише
Coolio.

## Гистерезис границ intensity + плавный переход вниз (девятый репорт)

**Баг: "один и тот же танец с перемешкой с idle breeze".** Причина — у
теста Coolio средняя intensity (по нашим же замерам, см. историю Phase 6-8)
оказалась близко к границе 0.5 между "light" и "active". Обычный шум/
дрожание сигнала туда-сюда пересекало эту единственную точку-порог
много раз в секунду. Каждое такое пересечение читалось кодом как "новый
вход в активное состояние" — а этот путь (в отличие от обычной
9-секундной ротации) переключает танец **мгновенно**, не дожидаясь конца
цикла. При частом дребезге получался быстрый дёрганый переключатель между
одним танцем и idle/shuffle — сам shuffle bag тут ни при чём, работал
правильно, просто получал команду "новый танец" гораздо чаще, чем должен был.

Исправлено — гистерезис: у каждой границы теперь ДВА порога вместо одного
(например для light/active: 0.55 на вход, 0.45 на выход) — сигнал должен
пройти весь этот "зазор", чтобы состояние реально сменилось. Обычное
дрожание в пределах пары сотых уже не переключает tier.

**Заодно сделал переход вниз (active → light/calm) более плавным** —
`tierDownFadeSeconds = 0.7` (было 0.35) именно для ЭТОГО перехода.
Не ждём конца лупа целиком (быстрый отклик на затихание музыки, который
тебе нравится, сохранён), но сам crossFade длиннее — ощущается как
затухание, а не обрыв. Переход вверх (light/calm → active) и обычная
9-секундная ротация внутри активного состояния — без изменений.

## Проверка

Погоняй тот же трек — переключения между танцем и idle/shuffle должны
стать значительно реже и осмысленнее (только на реальных, а не шумовых
изменениях энергии), а сам переход "музыка стихла → Idle" — чуть мягче,
не мгновенным обрывом жеста.

## Shuffle bag — равномерное покрытие пула танцев

Раньше выбор следующего танца был чистым независимым рандомом (только
правило "не тот же самый, что играет сейчас") — при пуле в 7 танцев это
статистически нормально давало то 3 повтора подряд за трек, то почти все 7
уникальных, в зависимости от чистого везения. Заменил на **shuffle bag**:
весь пул из 7 танцев перемешивается один раз, раздаётся по порядку без
повторов, и только когда "мешок" опустеет — тасуется заново (с проверкой,
чтобы новый мешок не начинался с того же танца, которым закончился старый).

Теперь за первые 7 переключений гарантированно увидишь все 7 разных
танцев, и только потом возможны повторы — предсказуемое разнообразие
вместо "то густо, то пусто". Пул акцентов (`uprock_brooklyn` и т.д.) пока
остался на чистом рандоме — не просили менять, но по той же логике можно
сделать так же, если тоже покажется неравномерным.

## Остаточные ~10% рывков (beat OFF) — гипотеза для следующего шага

Подтверждено, что оставшиеся рывки не связаны с кнопкой Beat — значит,
это либо (а) особенность самого crossFade между двумя РАЗНЫМИ mocap-клипами
(блендинг поз, которые изначально не были рассчитаны на переход друг в
друга — это ограничение подхода "чистые крестфейды", а не баг), либо (б)
переходы между tier'ами (calm/light/active) вниз — они, в отличие от
ротации внутри "активного" состояния, всё ещё переключаются мгновенно
(0.35с fade), не дожидаясь конца жеста, потому что тебе нравится быстрый
возврат в Idle при затихании музыки. Если растянуть crossFade именно на
понижающих переходах несколько дольше (не дожидаясь конца лупа целиком, но
хотя бы 0.6-0.8с вместо 0.35с) — это может сгладить и этот остаток, не
теряя отзывчивости. Скажи, если хочешь это тоже попробовать.

## Что изменилось: персонаж

Персонаж сменился с Quaternius-человека на **антропоморфную белку**,
сгенерированную через Tripo AI (text-to-3D) и заригованную на Mixamo.
Причина — у Quaternius в библиотеке анимаций был только один настоящий
танец (`Dance_Loop`), остальное — боевые/локомоционные клипы. Через Mixamo
доступна нормальная библиотека танцев, но там свой скелет — так что вместе
со сменой источника анимаций поменялся и сам персонаж.

Путь: Tripo (T-pose, PBR выключен после ошибки риггинга, ~6.3k вершин,
чистый меш без рига) → Mixamo Auto-Rigger (No Fingers skeleton — у лап нет
отдельных пальцев) → 13 FBX-файлов с танцами.

**Известный визуальный баг:** у скелета Mixamo нет кости для хвоста —
хвосту достаётся вес от ближайшей кости (видимо Hips), поэтому на резких
позах он может выглядеть слегка "отклеенным". Не критично на танцевальных
клипах, если будет сильно бросаться в глаза — правится в Blender (weight
paint, зажать хвост на одну кость).

## Технический пайплайн — GLTFLoader → FBXLoader

`scene.js` теперь использует `FBXLoader` (`three/addons/loaders/FBXLoader.js`)
вместо `GLTFLoader` для персонажа/анимаций. Старые `loadCharacter`/
`loadAnimationClips` (glTF, Quaternius) остались в файле нетронутыми — на
случай отката, просто не используются в `main.js`.

**Важный нюанс Mixamo, который стоил времени на отладку:** каждый
экспортированный файл называет свою анимацию внутри буквально `"mixamo.com"`
— одинаково для ЛЮБОГО клипа, что бы ты ни выбрал в интерфейсе. Если грузить
все файлы как есть, все клипы схлопнутся в одно имя и будут перезаписывать
друг друга в мапе. Поэтому `loadCharacterFBX`/`loadAnimationClipsFBX`
принимают `clipName` и переименовывают клип сразу при загрузке — эта
переименованная строка и есть теперь единственный слой конфигурации имён
(раньше был `animationMap`, теперь это просто параметр загрузки).

**Масштаб:** Mixamo-файлы в сантиметрах, сцена — в метрах. `loadCharacterFBX`
по умолчанию скейлит на `0.01`. Все 13 файлов (`Breathing_Idle` + 12
анимаций) пришли как **"With Skin"** (у каждого свой полный меш+скелет
внутри) — не страшно, для анимаций мы всё равно берём только
`fbx.animations`, а сам меш из этих файлов никогда не добавляется в сцену.

## Пул движений (Phase 10, расширенный)

Вместо одного `Dance_Loop` + одного акцента теперь два пула:

```js
MAIN_DANCE_POOL = ["hiphop_1..5", "samba", "silly"]   // основной танец
ACCENT_POOL = ["uprock_brooklyn", "uprock_breakdance", "twerk", "maraschino"]
```

Логика в `animationController.reactToAudio()` (не рандом каждый кадр, а
структурированная ротация):

- **intensity < 0.2** → `idle` (Breathing Idle)
- **0.2 ≤ intensity < 0.5** → `shuffle` (более сдержанный, чем полноценный танец)
- **intensity ≥ 0.5** → ротация по `MAIN_DANCE_POOL`: новый танец выбирается
  при входе в это состояние и каждые `tuning.danceRotateSeconds` (по
  умолчанию 9с) — случайно, но без повтора текущего подряд
- **strongBeat** во время активного танца → одноразовый клип из
  `ACCENT_POOL` (тоже без повтора подряд), автоматически возвращается в
  основной танец через `mixer.addEventListener('finished', ...)`

## Проверка

Открой через локальный сервер (см. ниже). Ожидай:
- в тихих местах — Breathing Idle
- на среднем уровне — Shuffling
- на активных участках — танец меняется каждые ~9 секунд сам по себе, плюс
  на сильных битах — короткие вставки (uprock/twerk/maraschino)
- пауза — всё замирает, включая процедурный присед/покачивание

Настройка на лету: `jerryAnim.tuning.danceRotateSeconds = 5` (чаще менять
танец), `jerryBeat.setStrongBeatRatio(1.5)` (реже акценты).

## Как запустить локально

ES modules не работают через `file://` — нужен локальный сервер:

```bash
cd music-dancer
python3 -m http.server 8000
```

Открыть http://localhost:8000 (добавь `?debug=1` для debug-панели с
volume/bass/mid/treble/intensity/beat-индикатором и OrbitControls).

## История Phase 1-9 (аудио-часть не менялась)

Вся аудио-часть (`audioPlayer.js`, `audioAnalyzer.js`, `beatDetector.js`,
intensity tracker) осталась ровно такой же, как в Phase 6-9 — сменился
только персонаж и источник анимаций, пайплайн `Audio → AudioAnalyzer →
AudioFeatures → AnimationController → Mixer` (ТЗ п.20) не тронут.

Коротко, что там было (детали — в истории чата/предыдущих версиях README):
- **Beat detection**: SMA-based adaptive threshold (не EMA — EMA "проглатывал"
  сами биты), `smoothingTimeConstant=0.2` на analyser (иначе гасится контраст
  удара), `minDecibels=-70/maxDecibels=-20` (дефолты Web Audio API рассчитаны
  на более тихий сигнал, чем обычно мастерят музыку — бас упирался в потолок)
- **Intensity**: `volume*2.6*0.35 + bass*0.65`, EMA-сглажено
- **Процедурная реакция**: приседание от сглаженного баса, покачивание
  корпусом от intensity, beat-акцент с плавным attack/decay (не мгновенный snap)
